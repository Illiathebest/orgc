# orgc

Компілятор декларативної моделі організації в конфігурації мережевої
інфраструктури з верифікацією інваріантів безпеки.

Адміністратор описує **організацію** — майданчики, мережеві сегменти, пристрої,
політики доступу — а не конфігурації окремих пристроїв. Коректність опису
перевіряється формально **до** застосування, а не після. З того самого опису
породжуються конфігурації різнорідного обладнання.

## Дві команди

```bash
orgc verify organization.yml    # діагностики або OK; ненульовий код виходу при помилках
orgc render organization.yml    # конфігурації пристроїв та інвентарі
```

Компілятор нічого не застосовує — він породжує текст і завершується. Жодних
мережевих з'єднань, жодних записів на обладнання. Застосування виконує окремий
ланцюг розгортання.

Приклад діагностики:

```
organization.yml:24:7  E006  пристрій rb750: немає дозволеного шляху
                             від control_node до мережі mgmt (192.168.10.0/24)
organization.yml:31:5  W001  мережа guest не має ознаки isolated
```

## Конвеєр

```
model → lower → IR → verify
                  └→ render → backends
```

Проміжне представлення не знає про вендорів: усі перевірки доводяться один раз
для всіх платформ. Бекенди підключаються через інтерфейс, ядро про них не знає.

Вихід детермінований — однаковий вхід дає побайтово однаковий результат.

## Інваріанти

| Код | Перевірка |
|---|---|
| E001 | Неперетин CIDR у межах сайту |
| E002 | Унікальність VLAN ID |
| E003 | Цілісність посилань: політика → мережа, пристрій → сайт |
| E004 | `mgmt_ip` належить мережі з роллю mgmt |
| E005 | Замкненість default-deny, відсутність правил any→any allow |
| E006 | Досяжність управління |
| E007 | Узгодженість адресного плану |
| E008 | Достатність ємності префікса |
| W001 | Guest-мережа без ізоляції |
| W002 | Можливість не підтримується цільовою платформою |
| W003 | Сайт профілю M без резервного каналу |

**E006** — перевірка, заради якої існує проєкт. Вона стверджує, що після
застосування конфігурації для кожного пристрою лишиться дозволений політиками
шлях від вузла керування до його management-мережі. Формулюється як задача
досяжності в графі, індукованому політиками.

## Структура

```text
.
├── orgc/                 компілятор (Go)
│   ├── cmd/orgc/         CLI
│   ├── internal/         model, lower, ir, verify, diag, backend
│   └── testdata/         valid, broken, golden
├── schema/               JSON Schema моделі організації
├── examples/             приклади organization.yml
├── docs/                 концепція, архітектура, ADR, звіти
├── ci/                   конвеєр CI, по файлу на стадію
├── ansible/              інвентарі та плейбуки розгортання
├── bootstrap/            compose-стеки вузлів стенда
├── runner-image/         образ середовища виконання CI
└── terraform/            модуль створення VM на стенді
```

## Збірка

```bash
cd orgc
go build ./cmd/orgc
go test ./...
```

Залежності — мінімальні, переважно стандартна бібліотека. Схема вбудована в
бінарник через `go:embed`, зовнішніх файлів компілятор не потребує.

## Конвеєр CI

```
build     збірка образу середовища виконання
lint      yamllint, ansible-lint, go vet, gofmt
verify    orgc verify — блокувальна стадія
render    orgc render, артефакти у Pull Request
smoke     read-only перевірка живого обладнання (manual)
```

Зламана модель валить пайплайн із конкретними кодами інваріантів.

## Стан

Компілятор у розробці. Реалізовано: модель даних і структурну валідацію.
Далі — проміжне представлення й інваріанти.

Терміни та критерії готовності — [docs/plan-2026-09.md](docs/plan-2026-09.md).

## Правила роботи

Зміни — лише через Pull Request у захищену `main`. Кожен PR проходить
lint → verify. Секрети — тільки `ansible-vault` або захищені змінні CI, у
відкритому вигляді в репозиторії їх немає.

Нетривіальні технологічні рішення фіксуються як ADR у `docs/adr/`.
