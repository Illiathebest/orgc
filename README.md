# orgc

Компілятор декларативної моделі організації в конфігурації мережевої
інфраструктури з верифікацією інваріантів безпеки.

Адміністратор описує організацію: майданчики, мережеві сегменти, пристрої,
політики доступу. Конфігурації окремих пристроїв він не пише. Коректність опису
перевіряється формально до застосування, і з того самого опису породжуються
конфігурації різнорідного обладнання.

## Дві команди

```bash
orgc verify organization.yml    # діагностики або OK; ненульовий код виходу при помилках
orgc render organization.yml    # конфігурації пристроїв та інвентарі
```

Компілятор нічого не застосовує: лише генерує текст і завершується, без
мережевих з'єднань і записів на обладнання. Застосування виконує окремий
ланцюг розгортання.

Приклад діагностики:

```
organization.yml:24:7  E006  пристрій rb750: немає дозволеного шляху
                             від control_node до мережі mgmt (192.168.10.0/24)
organization.yml:31:5  W001  мережа guest не має ознаки isolated
```

## Конвеєр

```
model → lower → IR → verify
                  └→ render → backends
```

Проміжне представлення не знає про вендорів: усі перевірки доводяться один раз
для всіх платформ. Бекенди підключаються через інтерфейс, ядро про них не знає.

Вихід детермінований: однаковий вхід дає побайтово однаковий результат.

## Інваріанти

| Код | Перевірка |
|---|---|
| E001 | Неперетин CIDR у межах моделі; між сайтами — лише з `allow_overlap` |
| E002 | Унікальність ідентифікаторів: VLAN ID у сайті; сайти, мережі, пристрої й сервери — у моделі |
| E003 | Цілісність посилань: політика → мережа, `control_node` → сайт і мережа, мережа з `gateway` → L3-шлюз сайту |
| E004 | `mgmt_ip` належить мережі з роллю mgmt того самого сайту |
| E005 | Збереження default-deny: немає правил any→any і `from: internet` |
| E006 | Досяжність керування |
| E007 | Узгодженість адресного плану |
| E008 | Достатність ємності префікса |
| E009 | L2-звʼязність сайту із зʼєднаннями: шлях кожного пристрою до шлюзу, доставка VLAN до access-портів |
| E010 | Топологія сайту із зʼєднаннями — дерево з коренем у L3-шлюзі |
| W001 | Guest-мережа без ізоляції або з доступом не лише до `internet` |
| W002 | Можливість не підтримується цільовою платформою |
| W003 | Сайт профілю M без резервного каналу |
| W004 | mgmt-сегмент відкрито не лише для вузла керування |
| W005 | Ієрархія ролей: рівень core → distribution → access зростає від шлюзу |

E006 — головна перевірка. Вона стверджує, що після застосування конфігурації
для кожного пристрою лишиться дозволений шлях від мережі вузла керування до його mgmt-мережі на порт
керування його платформи, який оголошує бекенд. Формулюється як задача
досяжності в графі топології (мережі й L3-шлюзи сайтів). Перевірка йде графом
топології, правила фільтрують потік на кожному шлюзі шляху. Правила
нетранзитивні, тож ланцюжок `A → B` і `B → C` шляхом не є.

Деталі моделі й повні визначення інваріантів наведено в [docs/data-model.md](docs/data-model.md).

## Бекенди

| Бекенд | Вихід |
|---|---|
| `routeros` | `.rsc` для MikroTik RouterOS |
| `aristaeos` | `.cfg` для Arista EOS |
| `ansible` | інвентар і групові змінні |
| `prometheus` | цілі моніторингу |
| `containerlab` | топологія для емулятора |

## Структура

```text
.
├── orgc/                 компілятор (Go)
│   ├── cmd/orgc/         CLI
│   ├── internal/         model, lower, ir, verify, diag, backend
│   └── testdata/         valid, broken, golden

├── docs/                 концепція, архітектура, ADR, звіти
├── ci/                   конвеєр CI, по файлу на стадію
├── ansible/              інвентарі та плейбуки розгортання

├── runner-image/         образ середовища виконання CI
└── terraform/            модуль створення VM на стенді
```

## Збірка

```bash
cd orgc
go build ./cmd/orgc
go test ./...
```

Залежностей мінімум, переважно стандартна бібліотека. Схема вбудована в
бінарник через `go:embed`, зовнішніх файлів компілятор не потребує.

## Конвеєр CI

```
build     збірка образу iac-runner з Go і перевірка go test у ньому
lint      yamllint, ansible-lint, gofmt, go vet
validate  orgc verify на прикладах моделей, go test
smoke     read-only перевірка живого RouterOS (manual)
```

`orgc verify` вимагає коду 0 для коректних моделей і саме коду 1 для зламаних,
тож модель із дефектом валить пайплайн конкретними кодами інваріантів.
Golden-тести бекендів виконуються в `go test`, тож зміна генерації без
оновлення еталонів валить пайплайн.
Подробиці — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), розділ 8.

## Стан

Компілятор працює від моделі до конфігурацій: `orgc verify` перевіряє схему й
інваріанти E001–E010, W001–W005, `orgc render` генерує конфігурації RouterOS і
Arista EOS, інвентар Ansible, цілі Prometheus і топологію containerlab. Вихід
побайтово детермінований і покритий golden-тестами. Далі: застосування на живому
обладнанні й в емуляторі та експерименти.

## Правила роботи

Зміни вносяться лише через Merge Request у захищену `main` в GitLab. Кожен MR
проходить lint → validate. Секрети зберігаються тільки в `ansible-vault` або в захищених
змінних CI, у відкритому вигляді в репозиторії їх немає.

Нетривіальні технологічні рішення фіксуються як ADR у `docs/adr/`.
