# ADR-001: Платформа віртуалізації лабораторного стенда

- **Статус:** Accepted для `pve-a`; вузол `pve-b` замінено [ADR-010](ADR-010-emulation-stand.md) (оновлення 2026-10-14)
- **Дата:** 2026-06-07; переглянуто 2026-06-08 після уточнення заліза
- **Контекст:** Доступне залізо (оновлено 2026-06-11) таке. (1) Основний ПК: 32 ГБ RAM, 1.5 ТБ SSD (додано 1 ТБ швидкого NVMe), Windows. Це робоча машина, тому повністю віддати її під стенд не можна. (2) Старий ноутбук: 16 ГБ RAM (8 + 8 після апгрейду), 128 ГБ диск, 2 ядра 2 ГГц. Його можна повністю виділити під експерименти. Фізичної мережі поки немає, згодом з'явиться MikroTik. Terraform-частина продукту має демонструвати реальний provisioning через API гіпервізора.

## Довідка по технологіях

- Proxmox VE – це найпопулярніший опенсорсний гіпервізор (KVM + контейнери LXC) для SMB/homelab. Він ставиться на голе залізо і керується через веб і REST API. Через API він і придатний для Terraform.
- Nested virtualization – це запуск гіпервізора всередині віртуальної машини (ВМ у ВМ). Сучасні CPU це підтримують. Втрата продуктивності становить ~10–20%, для конфігураційних експериментів це некритично.
- Гіпервізори для Windows-десктопа: Hyper-V (вбудований у Windows Pro), VMware Workstation Pro (з 2024 безкоштовний для особистого використання, найкраща підтримка nested virt), VirtualBox (простий, але nested-режим слабкий і повільний).

## Варіанти

| Критерій | A. Все на ПК (nested Proxmox під Windows) | B. Все на ноуті (Proxmox bare-metal) | **C. Два вузли: ноут bare-metal + ПК nested** |
|---|---|---|---|
| RAM під стенд | ~22–24 ГБ | 12 ГБ — не вміщає стенд (потрібно ~20) | 12 + ~20 ГБ |
| Завжди увімкнений control plane | ні (ПК — робоча машина) | так | так (ноут) |
| Демонстрація multi-site (S→M) | емуляція в межах одного вузла | ні | два реальні вузли = два «сайти» |
| Bare-metal для вимірів | ні | так | так (ноут) |
| Складність | низька | низька | середня (мережа між вузлами) |

## Рішення (рекомендація)

Обрано **варіант C (двовузловий стенд)**:

- Ноутбук → Proxmox VE bare-metal (вузол `pve-a`, «HQ»). Це постійно увімкнений вузол із control plane, на ньому VM з GitLab CE + Runner. Для GitLab достатньо 2 ядер і 12 ГБ, якщо його налаштувати: puma workers=2, знижена конкурентність sidekiq, registry лише за потреби. Якщо на практиці буде надто повільно, ролі вузлів міняємо місцями, а виміри фіксуємо.
- ПК → VMware Workstation Pro з однією великою VM (~20 ГБ), всередині якої працює Proxmox VE (вузол `pve-b`, «філія»). Ця VM вмикається на час експериментів. У ній працюють важкі компоненти: емуляція мережі (containerlab), цільові сервери, Wazuh.
- Обидва вузли стоять у домашній LAN. Для Terraform це два незалежні Proxmox API endpoints. Тому продукт «з коробки» демонструється в multi-site конфігурації (профіль M), а WireGuard-тунель між «сайтами» з'єднує два реальні вузли.

VMware Workstation обрано за [принципом відбору №1](README.md). Це найпопулярніший десктоп-гіпервізор з найзрілішою підтримкою nested virt. Hyper-V лишається запасним варіантом. Він вбудований, але nested KVM і мережеві мости в ньому примхливіші.

## Наслідки

- (+) Control plane працює постійно. Pipeline'и, моніторинг і drift detection працюють навіть тоді, коли ПК зайнятий або вимкнений.
- (+) Multi-site демонстрація на двох реальних вузлах.
- (−) 128 ГБ диска на ноуті (без змін). GitLab з образами займає ≈ 40–60 ГБ, тому треба стежити за місцем і чистити registry. Важкі дані (registry-кеш, снапшоти) зберігаються на pve-b з 1.5 ТБ.
- (−) 2 ядра на `pve-a`, тому CI-jobs можуть бути повільними. Важкі jobs можна направляти на runner у `pve-b` (runner tags). RAM більше не обмежує (16 ГБ).
- (−) Nested на ПК. Емуляція Cisco IOL/CHR у containerlab всередині nested Proxmox дає потрійну вкладеність. Це працює, але повільно. Заміри буде зроблено в M0.

## Оновлення 2026-10-14: що з рішення діє

- `pve-a` діє як записано. Proxmox VE на виділеному залізі несе VM `ctrl-01` (GitLab, раннер, реєстр образів) і `mon-01` (моніторинг).
- `pve-b` не побудовано. Він був потрібен для емуляції мережі в containerlab. Однак nested Proxmox у VMware дав би потрійну вкладеність для CHR (KVM усередині контейнера). Тому емуляцію перенесено на VM `clab-01` у Hyper-V, де рівнів вкладеності два. Рішення описано в [ADR-010](ADR-010-emulation-stand.md).
- Аргумент «REST API для Terraform» відпав, оскільки Terraform знято з роботи. Модуль у `terraform/` лишився як спадок. Вибору Proxmox для `pve-a` це не змінює. Він працює, і перенесення вузла нічого не дало б.

Решту тексту вище не змінено. Це запис рішення на свою дату.
