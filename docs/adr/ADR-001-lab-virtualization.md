# ADR-001: Платформа віртуалізації лабораторного стенда

- **Статус:** Proposed (rev. 2 — двовузлова схема)
- **Дата:** 2026-06-07; переглянуто 2026-06-08 після уточнення заліза
- **Контекст:** Доступне залізо (оновлено 2026-06-11): (1) основний ПК — 32 ГБ RAM, 1.5 ТБ SSD (додано 1 ТБ швидкого NVMe), Windows; це робоча машина, тому повністю віддати її під стенд не можна; (2) старий ноутбук — 16 ГБ RAM (8 + 8 після апгрейду), 128 ГБ диск, 2 ядра 2 ГГц; його можна виділити під експерименти повністю. Фізичної мережі поки немає (згодом MikroTik). Terraform-частина продукту має демонструвати реальний provisioning через API гіпервізора.

## Довідка по технологіях

- Proxmox VE — найпопулярніший опенсорсний гіпервізор (KVM + контейнери LXC) для SMB/homelab; ставиться на голе залізо, керується через веб і REST API. Саме API робить його придатним для Terraform.
- Nested virtualization — запуск гіпервізора всередині віртуальної машини (ВМ у ВМ). Сучасні CPU це підтримують; ціна — ~10–20% продуктивності, для конфігураційних експериментів некритично.
- Гіпервізори для Windows-десктопа: Hyper-V (вбудований у Windows Pro), VMware Workstation Pro (з 2024 безкоштовний для особистого використання, найкраща підтримка nested virt), VirtualBox (простий, але nested-режим слабкий і повільний).

## Варіанти

| Критерій | A. Все на ПК (nested Proxmox під Windows) | B. Все на ноуті (Proxmox bare-metal) | **C. Два вузли: ноут bare-metal + ПК nested** |
|---|---|---|---|
| RAM під стенд | ~22–24 ГБ | 12 ГБ — не вміщає стенд (потрібно ~20) | 12 + ~20 ГБ |
| Завжди увімкнений control plane | ні (ПК — робоча машина) | так | так (ноут) |
| Демонстрація multi-site (S→M) | емуляція в межах одного вузла | ні | два реальні вузли = два «сайти» |
| Bare-metal для вимірів | ні | так | так (ноут) |
| Складність | низька | низька | середня (мережа між вузлами) |

## Рішення (рекомендація)

**Варіант C — двовузловий стенд:**

- Ноутбук → Proxmox VE bare-metal (вузол `pve-a`, «HQ»). Постійно увімкнений вузол із control plane: VM з GitLab CE + Runner. 2 ядра / 12 ГБ для GitLab достатньо за умови тюнінгу (puma workers=2, знижена конкурентність sidekiq, registry — за потреби). Якщо на практиці буде надто повільно, ролі вузлів міняємо місцями (виміри зафіксувати).
- ПК → VMware Workstation Pro з однією великою VM (~20 ГБ), всередині якої Proxmox VE (вузол `pve-b`, «філія»). Вмикається на час експериментів; тут живуть важкі компоненти: емуляція мережі (containerlab), цільові сервери, Wazuh.
- Обидва вузли — у домашній LAN; з погляду Terraform це два незалежні Proxmox API endpoints, тому продукт «з коробки» демонструється у multi-site конфігурації (профіль M), а WireGuard-тунель між «сайтами» з'єднує два реальні вузли.

VMware Workstation обрано за [принципом відбору №1](README.md): найпопулярніший десктоп-гіпервізор з найзрілішим nested virt. Hyper-V — запасний варіант (вбудований, але nested KVM і мережеві мости в ньому примхливіші).

## Наслідки

- (+) Control plane живе постійно: pipeline'и, моніторинг і drift detection працюють навіть тоді, коли ПК зайнятий або вимкнений.
- (+) Multi-site демонстрація на двох реальних вузлах.
- (−) 128 ГБ диска на ноуті (без змін): GitLab + образи ≈ 40–60 ГБ, тому треба стежити за місцем і чистити registry. Важкі дані (registry-кеш, снапшоти) — на pve-b з 1.5 ТБ.
- (−) 2 ядра на `pve-a`: CI-jobs можуть бути повільними; важкі jobs можна таргетувати на runner у `pve-b` (runner tags). RAM більше не лімітує (16 ГБ).
- (−) Nested на ПК: емуляція Cisco IOL/CHR у containerlab всередині nested Proxmox дає потрійну вкладеність. Це працює, але повільно; заміри в M0.
