# ADR-004: Стек моніторингу та SIEM (модуль Security & Observability)

- **Статус:** Accepted для моніторингу (Prometheus, Alertmanager, Grafana, Loki). SIEM і нічний контроль дрейфу мають статус Rejected і зняті з роботи (оновлення 2026-10-14)
- **Дата:** 2026-06-07, переглянуто 2026-06-08
- **Контекст:** Модуль входить у MVP. Потрібен стек, який масштабується разом із профілями S/M/L і показує «безпеку як вимірюваний стан». Бюджет становить 32 ГБ на всю лабораторію.

## Довідка по технологіях

- Prometheus + Grafana – це де-факто стандарт моніторингу в DevOps. Prometheus збирає метрики (pull-модель, exporters), Grafana будує дашборди. Loki – це «Prometheus для логів» від Grafana Labs для легкого збору логів. Alertmanager маршрутизує алерти.
- Zabbix – це класичний моніторинг для enterprise та ISP, особливо популярний в Україні в телекомі. Він сильний у SNMP, однак GUI-центричний. Конфігурація зберігається в його БД поза Git, і це суперечить нашій IaC-тезі.
- VictoriaMetrics – це швидша й економніша заміна Prometheus, українська розробка. Вона сумісна з його екосистемою, але менш відома за межами спільноти моніторингу.
- Wazuh – це найпопулярніший опенсорсний SIEM/XDR. Агенти на хостах виконують контроль цілісності файлів (FIM), виявлення руткітів і перевірку CIS-комплаєнсу. Manager аналізує події за правилами, indexer (OpenSearch) зберігає їх і виконує пошук, dashboard надає веб-інтерфейс.
- CrowdSec – це легкий «колективний fail2ban». Він блокує атаки і належить до іншого класу рішень, ніж SIEM.

## Варіанти

### Метрики + логи (observability)

| Критерій | **A. Prometheus + Grafana + Loki** | B. Zabbix | C. VictoriaMetrics + Grafana |
|---|---|---|---|
| RAM на стенді | ~1–1.5 ГБ | ~1.5–2 ГБ (+SQL БД) | ~0.7–1 ГБ |
| Конфігурація як код | так (yaml, provisioning дашбордів) | частково (API/шаблони) | так |
| SNMP (Cisco/MikroTik) | snmp_exporter | нативно, сильна сторона | snmp_exporter |
| Логи | Loki + promtail/alloy — легкі | слабко | потрібен окремий стек |
| Екосистема/типовість для DevOps | еталонна | legacy-enterprise | сумісна з Prometheus |

### SIEM / host security

| Критерій | A. Wazuh all-in-one | B. Wazuh manager + Loki/Grafana як бекенд подій | C. CrowdSec + auditd |
|---|---|---|---|
| RAM | 4–8 ГБ (indexer = OpenSearch) | ~1–1.5 ГБ (без indexer/dashboard) | ~0.3 ГБ |
| FIM, виявлення руткітів, SCA/CIS-комплаєнс | так | так (це функції manager/agent) | ні (інший клас) |
| Повноцінний SIEM-пошук | так | обмежений (LogQL замість OpenSearch) | ні |
| Відповідність поняттю SIEM | так, але не влазить | так: агенти+правила ті самі, зріз у Grafana | підміна поняття SIEM |

## Рішення (рекомендація, rev. 2)

**Observability: варіант A**. Обрано Prometheus + Alertmanager + Grafana + Loki (node_exporter на серверах, snmp_exporter для Cisco/MikroTik). Це індустріальний стандарт, який повністю описується кодом. Дашборди й алерти генеруються з `organization.yml`. Zabbix відхилено через GUI-центричну конфігурацію, яка суперечить IaC-тезі. VictoriaMetrics розглядаємо лише як сумісну оптимізацію.

**SIEM: повний Wazuh single-node**. До нього входять manager, indexer і dashboard на окремій VM ~4 ГБ. На 32 ГБ він уміщається, і це найпоширеніший шлях. Він дає стандартні дашборди, повний пошук по подіях і типову конфігурацію з документації. Варіант лише з manager і подіями в Loki (rev. 1) переноситься в документацію продукту як *лайт-режим S-профілю для слабкого заліза*.

Drift detection (нічний `tofu plan` + `ansible --check`) надсилає звіти в Alertmanager. Так замикається теза «несанкціонована зміна конфігурації = інцидент безпеки».

## Наслідки

- (+) Канонічний досвід Wazuh: стандартні правила, звіти CIS-комплаєнсу, повний UI.
- (+) Grafana показує метрики, логи й drift, а Wazuh dashboard показує події безпеки. Алерти обох інтегруються в Alertmanager.
- (−) Окрема VM `wazuh-01` потребує +4 ГБ RAM. Це враховано в бюджеті M0.
- У профільній матриці S-lite означає manager-only→Loki, S/M означає single-node all-in-one. Профіль L означає Wazuh cluster + federated Prometheus, агенти й правила при цьому незмінні.

## Оновлення 2026-10-14: що з рішення діє

- Моніторинг діє як записано (варіант A). Prometheus, Alertmanager, Grafana і Loki розгорнуто на `mon-01`. Цілі Prometheus для серверів і мережевих пристроїв (`file_sd`) генерує `orgc render` з моделі організації. Цілі стенда – це його вихід з моделі стенда (`bootstrap/mon-01/prometheus/targets/`).
- SIEM (Wazuh) знято з роботи. Тема зосередилася на компіляції моделі й формальній перевірці інваріантів до застосування. Виявлення подій безпеки після застосування до неї не входить. VM `wazuh-01` не створювалася.
- Нічний контроль дрейфу (`tofu plan` + `ansible --check`) знято разом із Terraform. Безперервне узгодження стану з моделлю віднесено до перспектив.
- Профіль L прибрано з моделі, тому рядки профільної матриці про нього не діють.
