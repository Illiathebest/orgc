# ADR-005: Спосіб валідації моделі даних `organization.yml`

- **Статус:** Accepted — **JSON Schema (draft 2020-12) + `check-jsonschema`**
- **Дата:** 2026-06-14
- **Контекст:** Науковий стрижень продукту — **Organization-as-Data** (CONCEPT §2): адміністратор не пише код, а описує організацію у декларативному `organization.yml`, з якого платформа компілює конфігурації. Щоб ця модель була надійним «контрактом», її потрібно формально описати й автоматично перевіряти в CI (M1-core §2): зламана модель має валити пайплайн ще до того, як з неї почнуть генеруватися інвентарі та конфіги пристроїв (M2+). Питання цього ADR — **чим саме** описувати й перевіряти модель.

## Що ми валідуємо (вимоги до інструмента)

1. **Структура та типи:** наявність обов'язкових полів (`organization`, `profile`, `sites`), типи (рядок/число/масив), переліки (`profile ∈ {S, M, L}`), формати (CIDR, IP, діапазон VLAN 1–4094), діапазони портів.
2. **Декларативність:** опис моделі має сам бути **даними**, а не кодом — це прямо випливає з тези «Organization-as-Data». Контракт не повинен бути прив'язаний до мови програмування.
3. **CI-перевірка обома напрямками:** коректний приклад проходить, навмисно зламаний — валить пайплайн (DoD M1).
4. **Зручність для адміністратора:** підказки й підсвічування помилок прямо в редакторі (VS Code) під час заповнення `organization.yml`, до коміту.
5. **Бюджет:** інструмент має без проблем ставитися в образ `iac-runner` (python-база) і не тягнути важких залежностей.

> Поза цим ADR залишається **семантична/політикова** валідація (наприклад, неперетин CIDR між мережами, унікальність VLAN-ID у межах сайту, відповідність `policies` принципу default-deny з CONCEPT §6). Це окремий клас перевірок — до нього повернемося в M3+ (див. «Наслідки → майбутній шар політик»).

## Довідка по технологіях (простими словами)

- **JSON Schema** — це стандарт (специфікація IETF), яким *одним JSON/YAML-файлом* описують, **якою має бути структура іншого JSON/YAML-документа**: які поля обов'язкові, яких вони типів, які значення дозволені. Сама схема — це дані, а не програма. Перевіряльники (validators) є практично в кожній мові; редактори (VS Code) вміють підсвічувати помилки прямо під час набору. Остання версія — **draft 2020-12**. `check-jsonschema` — готова CLI-утиліта (Python), яка валідує YAML/JSON-файли проти схеми й зручно вбудовується в CI та pre-commit.
- **Pydantic** — популярна **Python-бібліотека**: модель описується як клас Python з типами полів, а бібліотека перевіряє й приводить дані до цих типів. Дуже потужна (можна писати будь-яку логіку перевірки кодом), має чудові повідомлення про помилки. Але опис моделі — це **код Python**, тобто прив'язка контракту до однієї мови.
- **Cerberus** — легка Python-бібліотека валідації: схема задається як **словник Python** (`dict`). Простіша за Pydantic, але теж Python-онлy і з помітно меншою спільнотою та екосистемою.
- **Rego / OPA (Open Policy Agent)** — окрема **мова політик** (Rego) і рушій (OPA) для перевірки правил поверх будь-яких структурованих даних. У CI запускається через `conftest`. Її сила — не опис «форми» документа, а складні **політики й зв'язки між сутностями** (умовні правила, крос-перевірки). Це інша, вища ліга задач, ніж структурна валідація; має свою криву навчання (новий DSL).

## Варіанти

| Критерій | **A. JSON Schema 2020-12 + check-jsonschema** | B. Pydantic v2 | C. Cerberus | D. Rego / OPA (conftest) |
|---|---|---|---|---|
| Опис моделі — це дані, а не код | **так** (файл-схема) | ні (клас Python) | ні (Python `dict`) | ні (код політик Rego) |
| Незалежність від мови | **так** (стандарт, валідатори всюди) | ні (Python) | ні (Python) | частково (окремий рушій) |
| Структура/типи/формати/переліки | так, нативно | так | так | незручно (це не його профіль) |
| Підсвічування помилок у редакторі (VS Code) | **так** (`yaml.schemas`, з коробки) | ні | ні | ні |
| Складна крос-польова логіка/політики | обмежено (`if/then`, `dependentSchemas`) | так (будь-який код) | слабко | **так, це його профіль** |
| Якість повідомлень про помилки | задовільна | відмінна | задовільна | добра |
| Популярність / типовість для опису конфігів | **еталонна** (k8s CRD, OpenAPI, GitHub Actions schema…) | висока (у Python-світі) | низька | росте в policy-as-code |
| Залежності в образі `iac-runner` | мінімальні (1 pip-пакет) | помірні | мінімальні | окремий бінар OPA/conftest |
| Виконання довільного коду під час валідації | **ні** (безпечно) | так (Python) | так (Python) | ні (sandboxed) |

## Рішення

**Варіант A — JSON Schema draft 2020-12, валідація в CI через `check-jsonschema`.**

Обґрунтування за принципом відбору №1 (популярність за замовчуванням) **і** за відповідністю задачі — тут вони збігаються:

1. **Декларативність — у яблучко концепції.** Уся теза продукту — «організація як **дані**». Природно, щоб і **контракт** цих даних теж був даними (файл-схема), а не Python-класом чи політикою-кодом. JSON Schema — єдиний варіант, де опис моделі лишається мовно-незалежним артефактом, який легко віддати рецензенту, іншому інструменту чи майбутньому веб-редактору анкети.
2. **Популярність і довіра.** JSON Schema — індустріальний стандарт опису структур: Kubernetes CRD, OpenAPI/Swagger, схеми GitHub Actions і GitLab CI — усе це JSON Schema. Рецензент диплома впізнає підхід; кадрова цінність висока.
3. **Поріг входу для адміністратора.** `yaml.schemas` у VS Code підсвічує помилки прямо під час заповнення `organization.yml` — це реалізує вимогу CONCEPT «мінімальні зусилля» ще до коміту, без жодного Python.
4. **Безпека й простота в CI.** Валідація не виконує довільного коду; `check-jsonschema` — один pip-пакет в образі `iac-runner`, тривіально дає негативний тест (зламаний приклад валить пайплайн).

**Чому відхилено інші:**
- **Pydantic** виграє ергономікою *в Python-коді*, але робить контракт кодом і прив'язує його до Python — це суперечить «data, not code». Залишаємо Pydantic як кандидата для **внутрішньої** реалізації генератора конфігів (M2+), де ми вже в Python і парсимо вже-валідний `organization.yml`; але **джерело істини й контракт** — JSON Schema, не Pydantic-клас.
- **Cerberus** — ті самі мінуси, що в Pydantic, плюс помітно менша спільнота й відсутність переваг. Програє за принципом №1.
- **Rego/OPA** вирішує *іншу* задачу — політики й крос-перевірки, а не «форму» документа. Це не конкурент JSON Schema, а **майбутній додатковий шар** (див. нижче).

## Наслідки

- (+) `schema/organization.schema.json` стає машиночитаним контрактом моделі; `validate`-стадія CI на образі `iac-runner` ловить структурні помилки на кожен MR.
- (+) Адміністратор отримує підказки в редакторі (підключення схеми через `# yaml-language-server: $schema=…` або `settings.json → yaml.schemas`).
- (+) Схема — мовно-незалежний артефакт: будь-який майбутній інструмент (веб-анкета, генератор) перевіряє ту саму схему.
- (−) **Семантика поза охопленням JSON Schema.** Структуру вона гарантує, але не зв'язки: неперетин CIDR, унікальність VLAN-ID, відповідність `policies` принципу default-deny (CONCEPT §6) JSON Schema перевіряє лише частково й громіздко.
  - **Майбутній шар політик:** ці перевірки закладаємо окремим кроком у M3+ — кандидати: OPA/`conftest` (policy-as-code) або невеликий Python-валідатор на базі вже-розпарсеної моделі. Це не скасовує цей ADR, а **нашаровується** поверх структурної валідації. Зафіксовано як відкрите рішення для майбутнього ADR.
- Профільна сумісність: схема описує `profile: S|M|L`, тож одна схема покриває всі профілі масштабування — перехід S→M (M5) не вимагає іншого контракту.

## Додаток А — базовий образ `iac-runner`: `python:3.12-slim` проти `ubuntu` / `alpine`

M1-core §1 фіксує базу `python:3.12-slim` і відсилає обґрунтування сюди (увесь тулінг — Python: ansible-core, NAPALM, лінтери, `check-jsonschema`).

| Критерій | **`python:3.12-slim` (Debian, glibc)** | `ubuntu:24.04` | `alpine` (musl) |
|---|---|---|---|
| Бінарна сумісність pip-wheels (cryptography, paramiko, lxml — залежності Ansible/NAPALM) | **так, glibc → готові wheels** | так (glibc), але Python ставити окремо | **ні: musl → багато пакетів компілюються з нуля** |
| Python «з коробки» | так, потрібна версія | ні (apt-інсталяція + налаштування) | так, але musl-нюанси |
| Розмір образу | малий (~150 МБ) | більший | найменший |
| Швидкість і надійність збірки образу | висока (wheels, без компіляторів) | середня | низька (потрібні build-deps, довгі білди) |
| Типовість для Python-тулінгу | **еталонна база** | загального призначення | ніша «мінімальний розмір» |

**Рішення:** `python:3.12-slim`. Вирішальний чинник — **glibc**: криптографічні й мережеві залежності Ansible/NAPALM мають готові бінарні wheels під glibc, тож збірка швидка й відтворювана без компіляторів у образі. `alpine` (musl) економить ~50–100 МБ ціною регулярної компіляції C-розширень і крихких білдів — невигідний обмін для CI-образу. `ubuntu` не дає переваг над `slim`, але важчий і вимагає ручної інсталяції Python. Це той випадок, де популярний вибір (`python:*-slim` — де-факто база Python-образів) і правильний збігаються.
