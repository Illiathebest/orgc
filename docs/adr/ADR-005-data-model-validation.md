# ADR-005: Спосіб валідації моделі даних `organization.yml`

- **Статус:** Accepted. Рішення: **JSON Schema (draft 2020-12) + `check-jsonschema`**
- Дата: 2026-06-14
- Контекст: основна ідея продукту – це Organization-as-Data (CONCEPT §2). Адміністратор описує організацію в декларативному `organization.yml`, і платформа компілює з нього конфігурації. Щоб модель була надійним «контрактом», її потрібно формально описати й автоматично перевіряти в CI (M1-core §2). Зламана модель має зупиняти пайплайн ще до того, як з неї почнуть генеруватися інвентарі та конфіги пристроїв (M2+). Цей ADR визначає, чим описувати й перевіряти модель.

## Що ми валідуємо (вимоги до інструмента)

1. Структура та типи. Сюди входять обов'язкові поля (`organization`, `profile`, `sites`), типи (рядок/число/масив) і переліки (`profile ∈ {S, M, L}`). Також перевіряються формати (CIDR, IP, діапазон VLAN 1–4094) і діапазони портів.
2. Декларативність: опис моделі сам має бути даними, як випливає з тези «Organization-as-Data». Контракт не повинен бути прив'язаний до мови програмування.
3. CI-перевірка в обидва боки. Коректний приклад проходить, а навмисно зламаний зупиняє пайплайн (DoD M1).
4. Зручність для адміністратора. Підказки й підсвічування помилок мають з'являтися в редакторі (VS Code) під час заповнення `organization.yml`, ще до коміту.
5. Бюджет. Інструмент має легко ставитися в образ `iac-runner` (python-база) і не тягнути важких залежностей.

> Семантична й політикова валідація лишається поза цим ADR. Наприклад, це неперетин CIDR між мережами, унікальність VLAN-ID у межах сайту і відповідність `policies` принципу default-deny з CONCEPT §6. Це окремий клас перевірок, до нього повернемося в M3+ (див. «Наслідки → майбутній шар політик»).

## Довідка щодо технологій

- JSON Schema – це стандарт (специфікація IETF) для опису структури JSON/YAML-документа іншим JSON/YAML-файлом. Схема задає обов'язкові поля, їхні типи й дозволені значення. Сама схема є даними. Перевіряльники (validators) є практично в кожній мові, а редактори (VS Code) підсвічують помилки під час набору. Остання версія має назву draft 2020-12. `check-jsonschema` – це готова CLI-утиліта (Python), яка валідує YAML/JSON-файли за схемою. Вона вбудовується в CI та pre-commit.
- Pydantic – це популярна Python-бібліотека. Модель описується як клас Python з типами полів, а бібліотека перевіряє дані й приводить їх до цих типів. Логіку перевірки можна писати будь-яким кодом, повідомлення про помилки докладні. Однак опис моделі при цьому є кодом Python, і контракт прив'язаний до однієї мови.
- Cerberus – це легка Python-бібліотека валідації, у якій схема задається словником Python (`dict`). Вона простіша за Pydantic, але теж працює лише з Python. Спільнота й екосистема в неї помітно менші.
- Rego / OPA (Open Policy Agent) – це окрема мова політик (Rego) і рушій (OPA) для перевірки правил поверх будь-яких структурованих даних. У CI вони запускаються через `conftest`. Вони призначені для складних політик і зв'язків між сутностями (умовні правила, крос-перевірки). Опис «форми» документа не є їхнім профілем. Це інший клас задач, ніж структурна валідація, і нова мова (DSL), яку треба вивчати.

## Варіанти

| Критерій | A. JSON Schema 2020-12 + check-jsonschema | B. Pydantic v2 | C. Cerberus | D. Rego / OPA (conftest) |
|---|---|---|---|---|
| Опис моделі — це дані, а не код | так (файл-схема) | ні (клас Python) | ні (Python `dict`) | ні (код політик Rego) |
| Незалежність від мови | так (стандарт, валідатори всюди) | ні (Python) | ні (Python) | частково (окремий рушій) |
| Структура/типи/формати/переліки | так, нативно | так | так | незручно (це не його профіль) |
| Підсвічування помилок у редакторі (VS Code) | так (`yaml.schemas`, з коробки) | ні | ні | ні |
| Складна крос-польова логіка/політики | обмежено (`if/then`, `dependentSchemas`) | так (будь-який код) | слабко | так, це його профіль |
| Якість повідомлень про помилки | задовільна | відмінна | задовільна | добра |
| Популярність / типовість для опису конфігів | еталонна (k8s CRD, OpenAPI, GitHub Actions schema…) | висока (у Python-світі) | низька | росте в policy-as-code |
| Залежності в образі `iac-runner` | мінімальні (1 pip-пакет) | помірні | мінімальні | окремий бінар OPA/conftest |
| Виконання довільного коду під час валідації | ні (безпечно) | так (Python) | так (Python) | ні (sandboxed) |

## Рішення

**Варіант A: JSON Schema draft 2020-12, валідація в CI через `check-jsonschema`**.

На варіант A вказують обидва критерії: [принцип відбору №1](README.md) (популярність за замовчуванням) і відповідність задачі.

1. Декларативність. Опис моделі є даними, як і вимагає концепція. Теза продукту звучить як «організація як дані», тому й контракт цих даних задається файлом-схемою без Python-класу чи коду політик. JSON Schema – це єдиний варіант, де опис моделі лишається мовно-незалежним артефактом. Такий артефакт легко передати іншому інструменту чи майбутньому веб-редактору анкети.
2. Популярність і довіра. JSON Schema – це індустріальний стандарт опису структур. На ній побудовано Kubernetes CRD, OpenAPI/Swagger, схеми GitHub Actions і GitLab CI.
3. Поріг входу для адміністратора. `yaml.schemas` у VS Code підсвічує помилки під час заповнення `organization.yml`, ще до коміту і без жодного Python. Так реалізується вимога CONCEPT «мінімальні зусилля».
4. Безпека й простота в CI. Валідація не виконує довільного коду. `check-jsonschema` – це один pip-пакет в образі `iac-runner`. Негативний тест, у якому зламаний приклад зупиняє пайплайн, отримується тривіально.

Чому відхилено інші варіанти:
- Pydantic зручніший у Python-коді, однак робить контракт кодом і прив'язує його до Python. Це суперечить принципу «data, not code». Pydantic лишається кандидатом для внутрішньої реалізації генератора конфігів (M2+). Там код уже написаний на Python і розбирає вже валідний `organization.yml`. Джерелом істини й контрактом лишається JSON Schema.
- Cerberus має ті самі мінуси, що й Pydantic, і помітно меншу спільноту без жодних переваг. Він програє за принципом №1.
- Rego/OPA розв'язує іншу задачу. Він перевіряє політики й зв'язки поверх уже описаної структури. Rego/OPA можна додати пізніше як окремий шар поверх JSON Schema (див. нижче).

## Наслідки

- (+) `schema/organization.schema.json` стає машиночитаним контрактом моделі. Стадія CI `validate` на образі `iac-runner` ловить структурні помилки на кожен MR.
- (+) Адміністратор отримує підказки в редакторі (підключення схеми через `# yaml-language-server: $schema=…` або `settings.json → yaml.schemas`).
- (+) Схема є мовно-незалежним артефактом. Будь-який майбутній інструмент (веб-анкета, генератор) перевіряє ту саму схему.
- (−) Семантика лежить поза охопленням JSON Schema. Структуру вона гарантує, а зв'язки не гарантує. Неперетин CIDR, унікальність VLAN-ID і відповідність `policies` принципу default-deny (CONCEPT §6) JSON Schema перевіряє лише частково й громіздко.
  - Майбутній шар політик. Ці перевірки закладаємо окремою роботою в M3+. Кандидатами є OPA/`conftest` (policy-as-code) або невеликий Python-валідатор на базі вже розібраної моделі. Такий шар не скасовує цей ADR і нашаровується поверх структурної валідації. Це зафіксовано як відкрите рішення для майбутнього ADR.
- Профільна сумісність. Схема описує `profile: S|M|L`, тому одна схема покриває всі профілі масштабування. Перехід S→M (M5) не вимагає іншого контракту.

## Додаток А — базовий образ `iac-runner`: `python:3.12-slim` проти `ubuntu` / `alpine`

План етапу M1 фіксував базу `python:3.12-slim`, обґрунтування наведено тут. Увесь тулінг написано на Python: ansible-core, NAPALM, лінтери, `check-jsonschema`.

| Критерій | `python:3.12-slim` (Debian, glibc) | `ubuntu:24.04` | `alpine` (musl) |
|---|---|---|---|
| Бінарна сумісність pip-wheels (cryptography, paramiko, lxml — залежності Ansible/NAPALM) | так, glibc → готові wheels | так (glibc), але Python ставити окремо | ні: musl → багато пакетів компілюються з нуля |
| Python «з коробки» | так, потрібна версія | ні (apt-інсталяція + налаштування) | так, але musl-нюанси |
| Розмір образу | малий (~150 МБ) | більший | найменший |
| Швидкість і надійність збірки образу | висока (wheels, без компіляторів) | середня | низька (потрібні build-deps, довгі білди) |
| Типовість для Python-тулінгу | еталонна база | загального призначення | ніша «мінімальний розмір» |

**Рішення:** `python:3.12-slim`. Вирішальним чинником є glibc. Криптографічні й мережеві залежності Ansible/NAPALM мають готові бінарні wheels під glibc, тому збірка швидка й відтворювана без компіляторів в образі. `alpine` (musl) економить ~50–100 МБ ціною регулярної компіляції C-розширень і крихких білдів. Для CI-образу такий обмін невигідний. `ubuntu` не дає переваг над `slim`, але важчий і вимагає ручної інсталяції Python. `python:*-slim` – це де-факто стандартна база Python-образів.
