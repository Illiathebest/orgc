# ADR-005: Спосіб валідації моделі даних `organization.yml`

- **Статус:** Accepted — **JSON Schema (draft 2020-12) + `check-jsonschema`**
- Дата: 2026-06-14
- Контекст: основна ідея продукту — Organization-as-Data (CONCEPT §2): адміністратор описує організацію у декларативному `organization.yml`, і платформа компілює з нього конфігурації. Щоб ця модель була надійним «контрактом», її потрібно формально описати й автоматично перевіряти в CI (M1-core §2): зламана модель має валити пайплайн ще до того, як з неї почнуть генеруватися інвентарі та конфіги пристроїв (M2+). Питання цього ADR — чим саме описувати й перевіряти модель.

## Що ми валідуємо (вимоги до інструмента)

1. Структура та типи: наявність обов'язкових полів (`organization`, `profile`, `sites`), типи (рядок/число/масив), переліки (`profile ∈ {S, M, L}`), формати (CIDR, IP, діапазон VLAN 1–4094), діапазони портів.
2. Декларативність: опис моделі сам має бути даними, як випливає з тези «Organization-as-Data». Контракт не повинен бути прив'язаний до мови програмування.
3. CI-перевірка обома напрямками: коректний приклад проходить, навмисно зламаний валить пайплайн (DoD M1).
4. Зручність для адміністратора: підказки й підсвічування помилок прямо в редакторі (VS Code) під час заповнення `organization.yml`, до коміту.
5. Бюджет: інструмент має без проблем ставитися в образ `iac-runner` (python-база) і не тягнути важких залежностей.

> Поза цим ADR залишається семантична/політикова валідація (наприклад, неперетин CIDR між мережами, унікальність VLAN-ID у межах сайту, відповідність `policies` принципу default-deny з CONCEPT §6). Це окремий клас перевірок, до нього повернемося в M3+ (див. «Наслідки → майбутній шар політик»).

## Довідка щодо технологій

- JSON Schema — стандарт (специфікація IETF), яким одним JSON/YAML-файлом описують, якою має бути структура іншого JSON/YAML-документа: які поля обов'язкові, яких вони типів, які значення дозволені. Сама схема — це дані. Перевіряльники (validators) є практично в кожній мові; редактори (VS Code) вміють підсвічувати помилки прямо під час набору. Остання версія — draft 2020-12. `check-jsonschema` — готова CLI-утиліта (Python), яка валідує YAML/JSON-файли проти схеми й вбудовується в CI та pre-commit.
- Pydantic — популярна Python-бібліотека: модель описується як клас Python з типами полів, а бібліотека перевіряє й приводить дані до цих типів. Логіку перевірки можна писати будь-яким кодом, повідомлення про помилки докладні. Опис моделі при цьому є кодом Python, тобто контракт прив'язаний до однієї мови.
- Cerberus — легка Python-бібліотека валідації: схема задається як словник Python (`dict`). Простіша за Pydantic, але теж працює лише з Python і має помітно меншу спільноту та екосистему.
- Rego / OPA (Open Policy Agent) — окрема мова політик (Rego) і рушій (OPA) для перевірки правил поверх будь-яких структурованих даних. У CI запускається через `conftest`. Призначена для складних політик і зв'язків між сутностями (умовні правила, крос-перевірки); опис «форми» документа не є її профілем. Це інший клас задач, ніж структурна валідація, і нова мова (DSL), яку треба вивчати.

## Варіанти

| Критерій | A. JSON Schema 2020-12 + check-jsonschema | B. Pydantic v2 | C. Cerberus | D. Rego / OPA (conftest) |
|---|---|---|---|---|
| Опис моделі — це дані, а не код | так (файл-схема) | ні (клас Python) | ні (Python `dict`) | ні (код політик Rego) |
| Незалежність від мови | так (стандарт, валідатори всюди) | ні (Python) | ні (Python) | частково (окремий рушій) |
| Структура/типи/формати/переліки | так, нативно | так | так | незручно (це не його профіль) |
| Підсвічування помилок у редакторі (VS Code) | так (`yaml.schemas`, з коробки) | ні | ні | ні |
| Складна крос-польова логіка/політики | обмежено (`if/then`, `dependentSchemas`) | так (будь-який код) | слабко | так, це його профіль |
| Якість повідомлень про помилки | задовільна | відмінна | задовільна | добра |
| Популярність / типовість для опису конфігів | еталонна (k8s CRD, OpenAPI, GitHub Actions schema…) | висока (у Python-світі) | низька | росте в policy-as-code |
| Залежності в образі `iac-runner` | мінімальні (1 pip-пакет) | помірні | мінімальні | окремий бінар OPA/conftest |
| Виконання довільного коду під час валідації | ні (безпечно) | так (Python) | так (Python) | ні (sandboxed) |

## Рішення

**Варіант A — JSON Schema draft 2020-12, валідація в CI через `check-jsonschema`.**

На варіант A вказують обидва критерії: [принцип відбору №1](README.md) (популярність за замовчуванням) і відповідність задачі.

1. Декларативність. Опис моделі є даними, як і вимагає концепція: теза продукту — «організація як дані», тож і контракт цих даних задається файлом-схемою, без Python-класу чи коду політик. JSON Schema — єдиний варіант, де опис моделі лишається мовно-незалежним артефактом, який легко передати іншому інструменту чи майбутньому веб-редактору анкети.
2. Популярність і довіра. JSON Schema — індустріальний стандарт опису структур: на ній побудовано Kubernetes CRD, OpenAPI/Swagger, схеми GitHub Actions і GitLab CI.
3. Поріг входу для адміністратора. `yaml.schemas` у VS Code підсвічує помилки прямо під час заповнення `organization.yml`, до коміту і без жодного Python. Так реалізується вимога CONCEPT «мінімальні зусилля».
4. Безпека й простота в CI. Валідація не виконує довільного коду; `check-jsonschema` — один pip-пакет в образі `iac-runner`, і негативний тест (зламаний приклад валить пайплайн) отримується тривіально.

Чому відхилено інші:
- Pydantic зручніший у Python-коді, але робить контракт кодом і прив'язує його до Python, що суперечить «data, not code». Pydantic лишається кандидатом для внутрішньої реалізації генератора конфігів (M2+), де код уже написаний на Python і розбирає вже валідний `organization.yml`. Джерелом істини й контрактом лишається JSON Schema.
- Cerberus має ті самі мінуси, що й Pydantic, і помітно меншу спільноту, не даючи переваг. Програє за принципом №1.
- Rego/OPA розв'язує іншу задачу: політики й крос-перевірки поверх уже описаної структури. Rego/OPA можна додати пізніше як окремий шар поверх JSON Schema (див. нижче).

## Наслідки

- (+) `schema/organization.schema.json` стає машиночитаним контрактом моделі; `validate`-стадія CI на образі `iac-runner` ловить структурні помилки на кожен MR.
- (+) Адміністратор отримує підказки в редакторі (підключення схеми через `# yaml-language-server: $schema=…` або `settings.json → yaml.schemas`).
- (+) Схема — мовно-незалежний артефакт: будь-який майбутній інструмент (веб-анкета, генератор) перевіряє ту саму схему.
- (−) Семантика поза охопленням JSON Schema. Структуру вона гарантує, зв'язки — ні: неперетин CIDR, унікальність VLAN-ID, відповідність `policies` принципу default-deny (CONCEPT §6) JSON Schema перевіряє лише частково й громіздко.
  - Майбутній шар політик: ці перевірки закладаємо окремою роботою в M3+. Кандидати — OPA/`conftest` (policy-as-code) або невеликий Python-валідатор на базі вже розібраної моделі. Такий шар не скасовує цей ADR і нашаровується поверх структурної валідації. Зафіксовано як відкрите рішення для майбутнього ADR.
- Профільна сумісність: схема описує `profile: S|M|L`, тож одна схема покриває всі профілі масштабування, і перехід S→M (M5) не вимагає іншого контракту.

## Додаток А — базовий образ `iac-runner`: `python:3.12-slim` проти `ubuntu` / `alpine`

План етапу M1 фіксував базу `python:3.12-slim`, а обґрунтування наведено тут (увесь тулінг — Python: ansible-core, NAPALM, лінтери, `check-jsonschema`).

| Критерій | `python:3.12-slim` (Debian, glibc) | `ubuntu:24.04` | `alpine` (musl) |
|---|---|---|---|
| Бінарна сумісність pip-wheels (cryptography, paramiko, lxml — залежності Ansible/NAPALM) | так, glibc → готові wheels | так (glibc), але Python ставити окремо | ні: musl → багато пакетів компілюються з нуля |
| Python «з коробки» | так, потрібна версія | ні (apt-інсталяція + налаштування) | так, але musl-нюанси |
| Розмір образу | малий (~150 МБ) | більший | найменший |
| Швидкість і надійність збірки образу | висока (wheels, без компіляторів) | середня | низька (потрібні build-deps, довгі білди) |
| Типовість для Python-тулінгу | еталонна база | загального призначення | ніша «мінімальний розмір» |

**Рішення:** `python:3.12-slim`. Вирішальний чинник — glibc: криптографічні й мережеві залежності Ansible/NAPALM мають готові бінарні wheels під glibc, тож збірка швидка й відтворювана без компіляторів у образі. `alpine` (musl) економить ~50–100 МБ ціною регулярної компіляції C-розширень і крихких білдів; для CI-образу такий обмін невигідний. `ubuntu` не дає переваг над `slim`, але важчий і вимагає ручної інсталяції Python. `python:*-slim` — де-факто стандартна база Python-образів.
