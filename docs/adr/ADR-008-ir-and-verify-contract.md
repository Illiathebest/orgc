# ADR-008: Проміжне представлення і контракт перевірок `verify`

- **Статус:** Accepted. Рішення: **IR з розібраними адресами, нерозвʼязаними посиланнями й індексом позицій. Інваріант – чиста функція над IR. Лише W дає код 0. Можливості платформи надходять через інтерфейс бекенда. E006 – досяжність у графі «мережі + шлюзи сайтів» з глобальним фільтром політики**
- Дата: 2026-10-09
- Контекст: структурний шар уже є. `model.Load` розбирає `organization.yml` і перевіряє його JSON Schema (ADR-005, ADR-006). Наступний шар – це інваріанти E001–E008 і W001–W004. Їхні точні визначення зафіксовано в семантиці моделі v2 (`docs/data-model.md`). Цей ADR визначає, над чим і як вони виконуються. Конвеєр компілятора має вигляд `model → lower → IR → verify`. IR не знає вендорів, бекенди підключаються через інтерфейс.

Від шести рішень цього ADR залежить уся реалізація інваріантів:

1. яку структуру має IR і як у ній зберігаються позиції у файлі;
2. що робить пониження з моделлю, у якій посилання не розвʼязуються;
3. який контракт у перевірки, у якому порядку вони виконуються і що буває при структурних помилках;
4. який код виходу, коли знайдено лише попередження;
5. що ядро має знати про платформу вже зараз, ще без генерації;
6. на якому графі й з якою семантикою фільтрації рахується E006.

## Вимоги

1. Детермінованість. Той самий вхід дає побайтово той самий вивід (правило проєкту, окремий експеримент). Порядок елементів IR і порядок діагностик не можуть залежати від обходу `map`.
2. Кожна діагностика інваріанта має рядок і шлях. Без рядка діагностика на моделі з двохсот пристроїв майже марна. З тієї ж причини `internal/model` прив'язує до рядка кожну структурну помилку.
3. Одне порушення дає один код. Експеримент E2 (мутаційне тестування) перевіряє, що мутація ловиться своїм кодом. Каскад «одна помилка → три діагностики різних кодів» робить E2 нечитабельним.
4. Ядро не знає вендорів. Порти керування для E006 і можливості для W002 надходять від бекенда.
5. Локальність. Усе збирається й тестується без стенда. Нових зовнішніх залежностей немає (`net/netip` входить у стандартну бібліотеку).

## Знахідка, що визначила рішення 1

`model.Load` повертає структури без позицій. Індекс «вузол YAML → рядок:колонка» (`locator` у `internal/model/position.go`) існує лише всередині `Load` і зникає після валідації схемою. Отже, без зміни `internal/model` вимогу 2 не виконати. Позиції мають пережити `Load`.

## 1. Структура IR

### Варіанти зберігання позицій

| Критерій | **A. Шлях в елементі + індекс «шлях → позиція» в `ir.Model`** | B. Окреме поле позиції для кожного поля IR | C. Посилання на вузол AST в елементі IR |
|---|---|---|---|
| Будь-яке поле досяжне для діагностики | так — `n.Path + ".cidr"` | лише ті, для яких заведено поле | так |
| Розмір структур IR | мінімальний | ×2 полів (`CIDR`, `CIDRPos`, …) | мінімальний |
| IR — чисте значення, без залежності від парсера | так | так | ні — IR імпортує `goccy/go-yaml/ast` |
| Можна побудувати IR у тесті без файлу | так, індекс порожній | так | ні |
| Ризик розходження шляху з позицією | один обхід AST будує обидва | немає | немає |

**Рішення – варіант A**. `model.Load` додатково повертає індекс `Positions`. Для кожного вузла документа (відображення, послідовність, скаляр) він зберігає позицію за читабельним шляхом у форматі `diag.PathFromPointer` (`sites[0].networks[2].cidr`). Індекс будується одним обходом AST. Це `map`, однак його лише читають за ключем і ніколи не обходять для виводу. Тому детермінованості він не загрожує.

### Склад IR

```
ir.Model
  Profile        Profile                 // S | M
  Sites          []*Site                 // порядок файлу
  Networks       []*Network              // усі мережі моделі, порядок файлу
  Devices        []*Device
  Servers        []*Server
  ControlNode    ControlNode
  Rules          []*Rule
  positions      індекс шлях → (рядок, колонка); метод At(path)

Site     { Name, AllowOverlap, Networks, Devices, Servers, Uplinks,
           Gateway *Device, GatewayCandidates []*Device, Origin }
Network  { Name, VLAN, Role, Prefix netip.Prefix, Gateway netip.Addr,
           Pool *Range{From, To netip.Addr}, Isolated, Site *Site, Origin }
Device   { Name, Type, OSVersion string, Role, MgmtIP netip.Addr, Site *Site, Origin }
Server   { Name, Roles, IP netip.Addr, Site *Site, Origin }
ControlNode { Site SiteRef, Network NetRef, IP netip.Addr, Origin }
Rule     { From, To Endpoint, Ports PortSet, Origin }
Endpoint { Kind: Network | Any | Internet; Name string; Net *Network }
PortSet  { Any bool; Ports []PortSpec{Proto, Port} — відсортовано }
Origin   { Path string }
```

- Елементи йдуть у порядку файлу. Такий порядок детермінований за побудовою і збігається з тим, як адміністратор читає модель. Сортування за іменем дало б ту саму стабільність, але відірвало б IR від джерела.
- Для перелічень заведено власні типи (`Role`, `DeviceType`, `DeviceRole`, `Profile`). Схема вже гарантувала допустимі значення, і перевірки не мають порівнювати рядкові літерали.
- Адреси зберігаються як `netip.Addr` і `netip.Prefix`. Це порівнювані значення без алокацій, з методами `Contains` і `Overlaps`. Їх і потребують E001, E004, E007.
- L3-шлюз сайту визначається за конвенцією моделі v2. Це пристрій з роллю `edge_router` або `firewall`. `lower` збирає всіх кандидатів у `GatewayCandidates` і заповнює `Gateway` лише тоді, коли кандидат рівно один. E003 бачить обидва дефекти («жодного», «кілька»). Решта перевірок працює лише з однозначним `Gateway`.
- Правила нормалізовано. `from`/`to` стають `Endpoint` з видом, і `any` та `internet` більше не треба впізнавати як рядки в кожній перевірці. `proto` без явного значення отримує `tcp`. Відсутні `ports` дають `PortSet{Any: true}` (будь-який протокол і порт, зокрема ICMP). Порти відсортовано. Поля `action` у IR немає, оскільки схема допускає лише `allow`.
- `os_version` лишається рядком. Формат версії залежить від платформи (`6.48.6` проти `4.29.2F`), тому розбирає її бекенд (рішення 5).

## 2. Пониження дефектної моделі

| Критерій | **A. Нерозвʼязане посилання лишається в IR** | B. `lower` повертає помилку | C. `lower` викидає елемент |
|---|---|---|---|
| Хто повідомляє про посилання | E003, з позицією і кодом | `lower` — поза системою кодів | ніхто |
| Інші інваріанти на тій самій моделі | виконуються | не виконуються | виконуються на неповній моделі мовчки |
| Скільки дефектів бачить адміністратор за прогін | усі | перший | частину |

**Рішення – варіант A**. `lower` ніколи не відмовляє через модель. Посилання, яке не знайшлося, зберігає імʼя, а вказівник лишається `nil` (`Endpoint{Kind: Network, Name: "srvers", Net: nil}`). Про таке посилання повідомляє E003. `lower` повертає помилку лише на дефект самого `orgc`.

Єдиний такий дефект зараз – це адреса, яку схема пропустила, а `net/netip` не розбирає. Після схеми такого не буває, оскільки шаблони `ipv4`/`cidr` відкидають провідні нулі так само, як `netip`. Якщо ж схема й IR колись розійдуться, `lower` поверне помилку з шляхом. Нульовий `netip.Addr{}` тут не підходить. Через нього кожен адресний інваріант мовчки пропустив би елемент, і модель пройшла б перевірку, якої не було. Тест підміняє адресу в обхід схеми і стежить за цим.

## 3. Контракт перевірок

```go
type Check struct {
    Code diag.Code
    Run  func(m *ir.Model, p backend.Platforms) []diag.Diagnostic
}
```

- Інваріант – це чиста функція над IR. Він не читає файлів, не змінює IR і не знає про інші перевірки. Тому кожен код тестується ізольовано, а для E1 можна виміряти час кожної перевірки окремо.
- Реєстр – це зріз із фіксованим порядком: E002, E003, E001, E007, E008, E004, E005, W002, E006, W001, W003, W004. Спершу йдуть ідентифікатори й посилання, на які спираються всі інші перевірки. Далі йдуть адресний план, ролі й платформи. Після них виконується E006, якому потрібні і адреси, і платформи. На вивід порядок не впливає (підсумковий перелік сортує `diag.Sort`), але він фіксує внутрішній хід обчислення.
- Структурні помилки зупиняють конвеєр. Якщо схема дала хоч одну помилку `S`, ні `lower`, ні інваріанти не запускаються. Так уже влаштований `model.Load`, який при помилках повертає `org == nil`. Структурно зламана модель не має однозначної семантики, і інваріанти на ній давали б шум.
- Каскадів немає. Інваріант пропускає елемент, передумову якого вже порушено і повідомлено іншим кодом (вимога 3). Усі такі випадки наведено в таблиці.

## 4. Код виходу при попередженнях

| Критерій | **A. Лише W → 0** | B. Будь-яке W → 1 |
|---|---|---|
| W004 «моніторинг з окремої мережі до mgmt» — легітимний випадок | проходить CI | блокує мердж |
| Попередження видно | так, у виводі й журналі CI | так |
| Відповідність конвенції компіляторів | так (`gcc` без `-Werror`) | так, як `-Werror` |

**Рішення – варіант A**. Код 1 означає «є хоча б одна діагностика з рівнем `Error`», і це вже реалізує `diag.HasErrors`. Рівень береться з самої діагностики, префікс коду на нього не впливає. Тому W002 рівня error (версія ОС поза діапазоном бекенда) дає 1. Для цього `internal/diag` і зберігає рівень окремо від коду. Коди виходу 0/1/2 не змінюються.

Прапорець на кшталт `--strict` не вводиться, оскільки сценарію, що його потребує, зараз немає.

## 5. Інтерфейс можливостей платформи

Тут описано мінімальну частину інтерфейсу бекенда, без якої не обійдуться E006 і W002. Генерація конфігурацій додасть свої методи пізніше.

```go
// package backend
type Platform interface {
    Type() string                                       // значення device.type: "mikrotik", "arista_eos"
    CheckVersion(v string) (ok bool, supported string)  // supported — діапазон текстом для діагностики
    ManagementPorts(v string) []PortSpec                // транспорт, яким Ansible застосовує конфігурацію
    Capabilities(v string) CapSet
}

type Platforms interface {
    Lookup(deviceType string) (Platform, bool)
}
```

- Назви можливостей нейтральні до вендора й визначені в ядрі: `L3Gateway`, `DHCPServer`, `NAT`, `StatefulFilter`, `ClientIsolation`. Перелік розширюється разом із моделлю.
- Які можливості потрібні, ядро визначає з IR. Які є, повідомляє бекенд. Наприклад, шлюзу сайту з мережею з `dhcp_pool` потрібен `DHCPServer`. Для правила `→ internet` потрібен `NAT`, для мережі `isolated: true` потрібен `ClientIsolation`. W002 рівня warning – це різниця цих множин.
- Порти залежать від версії, бо від версії залежить транспорт (у RouterOS 7 зʼявився REST API). RouterOS 6.x використовує TCP 8728 (`community.routeros.api`, `group_vars/mikrotik_routers`). Arista EOS використовує TCP 22 (`network_cli`). Діапазони версій фіксують реалізації платформ у `routeros` і `aristaeos`.
- Звʼязування виконується в `cmd/orgc`. `verify` отримує `Platforms` параметром, а реєстр з `routeros` і `aristaeos` збирає CLI. Ядро не імпортує жодного вендорського пакета. Тести перевірок підставляють фіктивну платформу.

## 6. Граф E006

Визначення E006 взято із семантики моделі v2. Для кожного пристрою *d* розглянемо потік від мережі вузла керування *N_c* до mgmt-мережі пристрою *N_m* на порт керування його платформи *P(d)*. Цей потік (1) дозволено політикою і (2) має L3-шлях.

Граф *G = (V, E)* складається з таких елементів:
- *V* – мережі моделі й L3-шлюзи сайтів (`Site.Gateway`);
- *E* – ребро «мережа – шлюз її сайту» для кожної мережі сайту, що має однозначний шлюз, і ребро «шлюз – шлюз» для кожної пари сайтів.

Міжсайтові зʼєднання повнозвʼязні незалежно від профілю. Модель v2 їх не описує, тому припущення про повнозвʼязність стосується моделі загалом. Профіль впливає лише на W003. Схема не забороняє профілю S мати кілька сайтів. Альтернатива «у профілі S шляху між сайтами немає» перетворила б E006 на багатосайтовій моделі S на заборону керування, якої ніхто не декларував.

Правила політики діють на кожному шлюзі шляху як фільтр потоку (*N_c*, *N_m*, порт). Потік пропускає правило з `from ∈ {N_c, any}`, `to ∈ {N_m, any}` і `ports` = будь-який або `ports ∩ P(d) ≠ ∅` з тим самим `proto`. Правила нетранзитивні. `A → B` і `B → C` не дають `A → C`, бо джерело пакета на проміжному сегменті не змінюється. Тому граф будується з топології, правила лише фільтрують потік. Якщо *N_c = N_m*, потік не перетинає шлюз і правило не потрібне.

Один обхід у ширину від *N_c* дає множину досяжних мереж. Далі для кожного пристрою перевіряємо, чи входить *N_m* у цю множину, і перебираємо правила. Складність становить O(|V| + |E| + |D|·|R|), де *D* – пристрої, *R* – правила. Повнозвʼязність дає |E| = O(|N| + |S|²) для *N* мереж і *S* сайтів.

Метод має обмеження. Політики моделі v2 глобальні, і кожен шлюз отримує ті самі правила. Тому фільтр на кожному шлюзі шляху однаковий, і за поточної моделі умова E006 рівносильна «правило дозволяє ∧ шлях існує». Граф однаково потрібен з двох причин:
1. він розрізняє причини відмови, які діагностика має називати: «немає правила», «правило без порту керування» (з переліком потрібних портів від бекенда), «немає L3-шляху» (мережа вузла керування чи mgmt-мережа без `gateway`, іншими словами без L3-інтерфейсу; сайт без однозначного шлюзу при мережах зі шлюзом уже дає E003, і E006 його пропускає);
2. формулювання лишається правильним, коли фільтрація стане неоднорідною (правила на рівні сайту) або зʼявляться описані міжсайтові канали. Тоді зміниться побудова *E* і фільтр на ребрі, алгоритм лишиться тим самим.

## Наслідки

- (+) Кожна діагностика інваріанта отримує рядок і шлях без зміни `diag`: `Diagnostic` уже має `Line`, `Column`, `Path`.
- (+) Перевірки тестуються ізольовано на IR, побудованому в коді, без файлів і без вендорських пакетів.
- (+) Один прогін показує всі дефекти моделі, і кожен дефект має один код. Це умова для E2.
- (+) Нова платформа додається реалізацією `Platform` і рядком у реєстрі `cmd/orgc`; ядро не змінюється.
- (−) `model.Load` змінює сигнатуру: повертає `*model.Document` (`File`, `Org`, `Positions`) замість `*Organization`. Тести `internal/model` оновлено під нову сигнатуру.
- (−) Правило «без каскадів» тримається на дисципліні, окремого механізму немає. Кожна перевірка сама знає, кого пропускати. Таблицю «без каскадів» (рішення 3) треба підтримувати разом із кодом. Її стережуть негативні тести «рівно один код на дефект».
- (−) Повнозвʼязність міжсайтових зʼєднань є припущенням. На моделі, де філія насправді не має каналу до HQ, E006 хибно скаже «OK». Ціна прийнятна, доки модель не описує канали з адресацією. Це обмеження моделі v2 зафіксовано в `docs/data-model.md`.
- Реалізацію виконуємо в такому порядку: пониження (`internal/lower`), каркас `verify` і платформи, далі інваріанти групами.
