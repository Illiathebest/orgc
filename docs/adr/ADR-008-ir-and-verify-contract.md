# ADR-008: Проміжне представлення і контракт перевірок `verify`

- **Статус:** Accepted — **IR з розібраними адресами, нерозвʼязаними посиланнями й індексом позицій; інваріант — чиста функція над IR; лише W → код 0; можливості платформи через інтерфейс бекенда; E006 — досяжність у графі «мережі + шлюзи сайтів» з глобальним фільтром політики**
- **Дата:** 2026-10-09
- **Контекст:** Структурний шар уже є: `model.Load` розбирає `organization.yml` і перевіряє його JSON Schema (ADR-005, ADR-006). Наступний шар — інваріанти E001–E008 і W001–W004. Їхні точні визначення зафіксовано в семантиці моделі v2 (`docs/data-model.md`); цей ADR визначає, над чим і як вони виконуються. Конвеєр компілятора: `model → lower → IR → verify`, IR не знає вендорів, бекенди підключаються через інтерфейс.

Питання ADR — шість рішень, від яких залежить уся реалізація інваріантів:

1. яку структуру має IR і як у ній зберігаються позиції у файлі;
2. що робить пониження з моделлю, у якій посилання не розвʼязуються;
3. який контракт у перевірки, у якому порядку вони виконуються і що буває при структурних помилках;
4. який код виходу, коли знайдено лише попередження;
5. що ядро має знати про платформу вже зараз, ще без генерації;
6. на якому графі й з якою семантикою фільтрації рахується E006.

## Вимоги

1. Детермінованість. Той самий вхід — побайтово той самий вивід (правило проєкту, окремий експеримент). Порядок елементів IR і порядок діагностик не можуть залежати від обходу `map`.
2. Кожна діагностика інваріанта має рядок і шлях. Без рядка діагностика на моделі з двохсот пристроїв майже марна; з тієї ж причини `internal/model` прив'язує до рядка кожну структурну помилку.
3. Одне порушення — один код. Експеримент E2 (мутаційне тестування) перевіряє, що мутація ловиться саме своїм кодом. Каскад «одна помилка → три діагностики різних кодів» робить E2 нечитабельним.
4. Ядро не знає вендорів. Порти керування для E006 і можливості для W002 надходять від бекенда.
5. Локальність. Усе збирається й тестується без стенда; жодних нових зовнішніх залежностей (`net/netip` — стандартна бібліотека).

## Знахідка, що визначила рішення 1

`model.Load` повертає структури без позицій. Індекс «вузол YAML → рядок:колонка» (`locator` у `internal/model/position.go`) існує лише всередині `Load` і зникає після валідації схемою. Тобто вимога 2 неможлива без зміни `internal/model`: позиції мають пережити `Load`.

## 1. Структура IR

### Варіанти зберігання позицій

| Критерій | **A. Шлях в елементі + індекс «шлях → позиція» в `ir.Model`** | B. Окреме поле позиції для кожного поля IR | C. Посилання на вузол AST в елементі IR |
|---|---|---|---|
| Будь-яке поле досяжне для діагностики | так — `n.Path + ".cidr"` | лише ті, для яких заведено поле | так |
| Розмір структур IR | мінімальний | ×2 полів (`CIDR`, `CIDRPos`, …) | мінімальний |
| IR — чисте значення, без залежності від парсера | так | так | ні — IR імпортує `goccy/go-yaml/ast` |
| Можна побудувати IR у тесті без файлу | так, індекс порожній | так | ні |
| Ризик розходження шляху з позицією | один обхід AST будує обидва | немає | немає |

**Рішення — A.** `model.Load` повертає додатково індекс `Positions`: для кожного вузла документа (відображення, послідовність, скаляр) — його позиція за читабельним шляхом у форматі `diag.PathFromPointer` (`sites[0].networks[2].cidr`). Індекс будується одним обходом AST. Це `map`, але його лише читають за ключем і ніколи не обходять для виводу, тож детермінованості він не загрожує.

### Склад IR

```
ir.Model
  Profile        Profile                 // S | M
  Sites          []*Site                 // порядок файлу
  Networks       []*Network              // усі мережі моделі, порядок файлу
  Devices        []*Device
  Servers        []*Server
  ControlNode    ControlNode
  Rules          []*Rule
  positions      індекс шлях → (рядок, колонка); метод At(path)

Site     { Name, AllowOverlap, Networks, Devices, Servers, Uplinks,
           Gateway *Device, GatewayCandidates []*Device, Origin }
Network  { Name, VLAN, Role, Prefix netip.Prefix, Gateway netip.Addr,
           Pool *Range{From, To netip.Addr}, Isolated, Site *Site, Origin }
Device   { Name, Type, OSVersion string, Role, MgmtIP netip.Addr, Site *Site, Origin }
Server   { Name, Roles, IP netip.Addr, Site *Site, Origin }
ControlNode { Site SiteRef, Network NetRef, IP netip.Addr, Origin }
Rule     { From, To Endpoint, Ports PortSet, Origin }
Endpoint { Kind: Network | Any | Internet; Name string; Net *Network }
PortSet  { Any bool; Ports []PortSpec{Proto, Port} — відсортовано }
Origin   { Path string }
```

- Порядок елементів — порядок у файлі. Він детермінований за побудовою і збігається з тим, як адміністратор читає модель; сортування за іменем дало б ту саму стабільність, але відірвало б IR від джерела.
- Перелічення — власні типи (`Role`, `DeviceType`, `DeviceRole`, `Profile`), а не рядки: схема вже гарантувала допустимі значення, а перевірки не мають порівнювати рядкові літерали.
- Адреси — `netip.Addr` і `netip.Prefix`. Порівнювані значення без алокацій, з `Contains` і `Overlaps` — саме те, що потрібно E001, E004, E007.
- L3-шлюз сайту визначається за конвенцією моделі v2: пристрій з роллю `edge_router` або `firewall`. `lower` збирає всіх кандидатів у `GatewayCandidates` і заповнює `Gateway` лише тоді, коли кандидат рівно один. E003 бачить обидва дефекти («жодного», «кілька»), а решта перевірок працює лише з однозначним `Gateway`.
- Правила нормалізовано. `from`/`to` — `Endpoint` з видом (`any` і `internet` перестають бути рядками, які треба впізнавати в кожній перевірці); `proto` без явного значення — `tcp`; відсутні `ports` — `PortSet{Any: true}` (будь-який протокол і порт, зокрема ICMP); порти відсортовано. `action` у IR немає: схема допускає лише `allow`.
- `os_version` лишається рядком. Формат версії — властивість платформи (`6.48.6` проти `4.29.2F`), розбирає її бекенд (рішення 5).

## 2. Пониження дефектної моделі

| Критерій | **A. Нерозвʼязане посилання лишається в IR** | B. `lower` повертає помилку | C. `lower` викидає елемент |
|---|---|---|---|
| Хто повідомляє про посилання | E003, з позицією і кодом | `lower` — поза системою кодів | ніхто |
| Інші інваріанти на тій самій моделі | виконуються | не виконуються | виконуються на неповній моделі мовчки |
| Скільки дефектів бачить адміністратор за прогін | усі | перший | частину |

**Рішення — A.** `lower` не відмовляє через модель ніколи. Посилання, яке не знайшлося, зберігає імʼя, а вказівник лишається `nil` (`Endpoint{Kind: Network, Name: "srvers", Net: nil}`); його повідомляє E003. `lower` повертає помилку лише на дефект самого `orgc`.

Єдиний такий дефект зараз — адреса, яку схема пропустила, а `net/netip` не розбирає. Після схеми такого не буває: шаблони `ipv4`/`cidr` відкидають провідні нулі так само, як `netip`. Але якщо схема й IR колись розійдуться, `lower` повертає помилку з шляхом, а не нульовий `netip.Addr{}`: нульова адреса змусила б кожен адресний інваріант мовчки пропустити елемент, і модель пройшла б перевірку, якої не було. Тест підміняє адресу в обхід схеми і стежить за цим.

## 3. Контракт перевірок

```go
type Check struct {
    Code diag.Code
    Run  func(m *ir.Model, p backend.Platforms) []diag.Diagnostic
}
```

- Інваріант — чиста функція над IR. Не читає файлів, не змінює IR, не знає про інші перевірки. Тому кожен код тестується ізольовано, а для E1 можна виміряти час кожної перевірки окремо.
- Реєстр — зріз із фіксованим порядком: E002, E003, E001, E007, E008, E004, E005, W002, E006, W001, W003, W004. Спершу ідентифікатори й посилання (на них спираються всі інші), потім адресний план, ролі, платформи, і E006, якому потрібні й адреси, і платформи. На вивід порядок не впливає (підсумковий перелік сортує `diag.Sort`), але він фіксує внутрішній хід обчислення.
- Структурні помилки зупиняють конвеєр. Якщо схема дала хоч одну помилку `S`, ні `lower`, ні інваріанти не запускаються. Так уже влаштований `model.Load`: при помилках він повертає `org == nil`. Структурно зламана модель не має однозначної семантики, і інваріанти на ній давали б шум.
- Без каскадів. Інваріант пропускає елемент, передумову якого вже порушено і повідомлено іншим кодом (вимога 3):

| Перевірка | Пропускає, якщо | Бо це вже |
|---|---|---|
| E006 | вузол керування або його мережа не розвʼязалися | E003 |
| E006 | `mgmt_ip` пристрою не лежить у mgmt-мережі його сайту | E004 |
| E006 | платформа не знає версії ОС пристрою | W002 (error) |
| E007 (адреса вузла керування) | мережа вузла керування не розвʼязалася | E003 |
| W004, W001, E005 | кінці правила не розвʼязалися | E003 |
| E001 (правило між мережами з дозволеним перетином) | кінці правила не розвʼязалися | E003 |
| E001 (правило між мережами з дозволеним перетином) | правило `any → any` | E005 |
| E007 | мережа замала для свого пулу, шлюзу й статичних адрес | E008 |
| E007 (належність `mgmt_ip` до мережі) | завжди: E004 вимагає більшого — mgmt-мережі свого сайту | E004 |

## 4. Код виходу при попередженнях

| Критерій | **A. Лише W → 0** | B. Будь-яке W → 1 |
|---|---|---|
| W004 «моніторинг з окремої мережі до mgmt» — легітимний випадок | проходить CI | блокує мердж |
| Попередження видно | так, у виводі й журналі CI | так |
| Відповідність конвенції компіляторів | так (`gcc` без `-Werror`) | так, як `-Werror` |

**Рішення — A.** Код 1 означає «є хоча б одна діагностика з рівнем `Error`», що вже реалізує `diag.HasErrors`. Рівень береться з самої діагностики, а не з префікса коду, тому W002 рівня error (версія ОС поза діапазоном бекенда) дає 1. Саме для цього `internal/diag` зберігає рівень окремо від коду. Коди виходу 0/1/2 не змінюються.

Прапорець на кшталт `--strict` не вводиться: жодного сценарію, що його потребує, зараз немає.

## 5. Інтерфейс можливостей платформи

Це мінімальна частина інтерфейсу бекенда: та, без якої не обійдуться E006 і W002. Генерація конфігурацій додасть свої методи пізніше.

```go
// package backend
type Platform interface {
    Type() string                                       // значення device.type: "mikrotik", "arista_eos"
    CheckVersion(v string) (ok bool, supported string)  // supported — діапазон текстом для діагностики
    ManagementPorts(v string) []PortSpec                // транспорт, яким Ansible застосовує конфігурацію
    Capabilities(v string) CapSet
}

type Platforms interface {
    Lookup(deviceType string) (Platform, bool)
}
```

- Назви можливостей нейтральні до вендора й визначені в ядрі: `L3Gateway`, `DHCPServer`, `NAT`, `StatefulFilter`, `ClientIsolation`. Перелік розширюється разом із моделлю.
- Що потрібно, вирішує ядро з IR; що є, каже бекенд. Наприклад, шлюзу сайту з мережею з `dhcp_pool` потрібен `DHCPServer`, з правилом `→ internet` — `NAT`, з мережею `isolated: true` — `ClientIsolation`. W002 рівня warning — різниця цих множин.
- Порти залежать від версії, бо від версії залежить транспорт (у RouterOS 7 зʼявився REST API). Для поточних платформ: RouterOS 6.x — TCP 8728 (`community.routeros.api`, `group_vars/mikrotik_routers`), Arista EOS — TCP 22 (`network_cli`). Діапазони версій фіксують реалізації платформ у `routeros` і `aristaeos`.
- Звʼязування — у `cmd/orgc`. `verify` отримує `Platforms` параметром; реєстр з `routeros` і `aristaeos` збирає CLI. Ядро не імпортує жодного вендорського пакета, а тести перевірок підставляють фіктивну платформу.

## 6. Граф E006

Визначення E006 — з семантики моделі v2: для кожного пристрою *d* потік від мережі вузла керування *N_c* до mgmt-мережі пристрою *N_m* на порт керування його платформи *P(d)* (1) дозволено політикою і (2) має L3-шлях.

Граф *G = (V, E)*:
- *V* — мережі моделі й L3-шлюзи сайтів (`Site.Gateway`);
- *E* — ребро «мережа — шлюз її сайту» для кожної мережі сайту, що має однозначний шлюз; ребро «шлюз — шлюз» для кожної пари сайтів.

Міжсайтові зʼєднання повнозвʼязні незалежно від профілю. Модель v2 їх не описує; припущення про повнозвʼязність стосується моделі загалом, а не профілю M. Профіль впливає лише на W003. Схема не забороняє профілю S мати кілька сайтів, і альтернатива — «у профілі S шляху між сайтами немає» — перетворила б E006 на багатосайтовій моделі S на заборону керування, якої ніхто не декларував.

Фільтр. Правила політики діють на кожному шлюзі шляху як фільтр потоку (*N_c*, *N_m*, порт). Потік пропускає правило з `from ∈ {N_c, any}`, `to ∈ {N_m, any}` і `ports` = будь-який або `ports ∩ P(d) ≠ ∅` з тим самим `proto`. Правила нетранзитивні: `A → B` і `B → C` не дають `A → C`, бо джерело пакета на проміжному сегменті не змінюється; тому граф будується з топології, а не з правил. Якщо *N_c = N_m*, потік не перетинає шлюз і правило не потрібне.

Алгоритм. Один обхід у ширину від *N_c* дає множину досяжних мереж; далі для кожного пристрою — перевірка *N_m* у цій множині і перебір правил. Складність O(|V| + |E| + |D|·|R|), де *D* — пристрої, *R* — правила; повнозвʼязність дає |E| = O(|N| + |S|²) для *N* мереж і *S* сайтів.

Обмеження методу: політики моделі v2 глобальні, тобто кожен шлюз отримує ті самі правила. Тож фільтр на кожному шлюзі шляху однаковий, і за поточної моделі умова E006 рівносильна «правило дозволяє ∧ шлях існує». Граф однаково потрібен з двох причин:
1. він розрізняє причини відмови, а діагностика має їх називати: «немає правила», «правило без порту керування» (з переліком потрібних портів від бекенда), «немає L3-шляху» (сайт без шлюзу чи з двома);
2. формулювання лишається правильним, коли фільтрація стане неоднорідною (правила на рівні сайту) або зʼявляться описані міжсайтові канали — зміниться побудова *E* і фільтр на ребрі, не алгоритм.

## Наслідки

- (+) Кожна діагностика інваріанта отримує рядок і шлях без зміни `diag`: `Diagnostic` уже має `Line`, `Column`, `Path`.
- (+) Перевірки тестуються ізольовано на IR, побудованому в коді, без файлів і без вендорських пакетів.
- (+) Один прогін показує всі дефекти моделі, а кожен — одним кодом. Це умова для E2.
- (+) Нова платформа додається реалізацією `Platform` і рядком у реєстрі `cmd/orgc`; ядро не змінюється.
- (−) `model.Load` змінює сигнатуру: повертає `*model.Document` (`File`, `Org`, `Positions`) замість `*Organization`. Тести `internal/model` оновлено під нову сигнатуру.
- (−) Правило «без каскадів» — дисципліна, а не механізм: кожна перевірка сама знає, кого пропускати. Таблицю «без каскадів» (рішення 3) треба підтримувати разом із кодом; негативні тести «рівно один код на дефект» її стережуть.
- (−) Повнозвʼязність міжсайтових зʼєднань — припущення. На моделі, де філія насправді не має каналу до HQ, E006 скаже «OK» хибно. Ціна прийнятна, доки модель не описує канали з адресацією; це обмеження моделі v2 зафіксовано в `docs/data-model.md`.
- Порядок реалізації: пониження (`internal/lower`), каркас `verify` і платформи, далі інваріанти групами.
