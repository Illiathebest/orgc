# ADR-009: Інтерфейс рендеру і контракт виходу `orgc render`

- **Статус:** Accepted — **рендер пристрою — метод платформи, рендер рівня моделі — окремі генератори; `render` лише після чистого `verify`; каталог виходу належить `orgc` і перезаписується повністю; порти — з моделі, для сайту без зʼєднань — конвенція платформи (поправка 2026-10-12); еталон інвентаря — вихід з моделі поточного стенда**
- **Дата:** 2026-10-12
- Контекст: `orgc verify` перевіряє модель повністю (ADR-008), а `orgc render` поки заглушка. Генерація має дати конфігурації RouterOS і Arista EOS, інвентар Ansible, цілі Prometheus і топологію containerlab. Від рішень нижче залежать усі бекенди, golden-тести й експеримент E5 (локальність diff): якщо зміна одного правила моделі тягне зміни в непов'язаних файлах чи лишає застарілі файли, E5 вимірюватиме шум.

Питання ADR — сім рішень:

1. як бекенд отримує модель і що повертає;
2. яке дерево виходу і що буває з наявним каталогом;
3. звідки бекенд знає фізичні порти, яких модель не описує;
4. що генерується для Ansible і що вважати еталоном;
5. як правила політики стають конфігурацією на кожній платформі;
6. з чого будується топологія containerlab;
7. що гарантує побайтову детермінованість.

## Вимоги

1. Ядро не знає вендорів (ADR-008): `ir`, `lower`, `verify` і інтерфейс `backend` не імпортують платформних пакетів.
2. Детермінованість: той самий вхід — побайтово той самий вихід, зокрема між версіями `orgc`, якщо генерація не змінювалась.
3. Конфігурація генерується лише з перевіреної моделі: те, що `verify` вважає помилкою, не має шансу потрапити на обладнання.
4. Наявні плейбуки (`smoke_routeros.yml`, `linux.yml`) працюють на згенерованому інвентарі без змін.
5. Секрети не з'являються у виході: лише посилання на `ansible-vault` чи змінні середовища.

## 1. Інтерфейс рендеру

```go
// package backend
type File struct {
    Path string // відносний, через "/", напр. "configs/hq/rb750.rsc"
    Data []byte
}

type Platform interface {
    // ... методи ADR-008: Type, CheckVersion, ManagementPorts, Capabilities
    Render(m *ir.Model, d *ir.Device) []File
}

type Generator interface {
    Name() string
    Generate(m *ir.Model, p Platforms) []File
}
```

- Конфігурація пристрою — метод платформи: усе, що стосується синтаксису RouterOS чи EOS, живе в її пакеті.
- Ansible, Prometheus і containerlab описують модель цілком, а не один пристрій, тому це окремі генератори з реєстром у `cmd/orgc` у фіксованому порядку.
- Коли генераторові потрібне знання про платформу (група інвентаря й змінні підключення, вид вузла containerlab), він питає платформу через додатковий інтерфейс, який платформа реалізує, наприклад `AnsibleTarget` чи `LabNode`. Генератор вендорів не знає.
- Вхід — лише IR і реєстр платформ. Повернення помилки не передбачено: модель уже перевірена, а неможливість згенерувати пристрій — це W002 рівня помилки, яку `verify` повідомив раніше.

`orgc render <модель> -o <каталог>` спершу виконує той самий конвеєр, що й `verify`:

| Результат `verify` | `render` |
|---|---|
| помилки (зокрема W002 рівня помилки) | діагностики, код 1, жодного файлу |
| лише попередження | діагностики, генерація, код 0 |
| нічого | генерація, код 0 |

## 2. Дерево виходу

```
<каталог>/
  .orgc-output                         маркер: каталог створено orgc
  configs/<site>/<device>.rsc          RouterOS
  configs/<site>/<device>.cfg          Arista EOS
  ansible/hosts.yml
  ansible/group_vars/<group>/main.yml
  prometheus/targets/<job>.json        file_sd
  containerlab/<organization>.clab.yml
```

Імена каталогів і файлів беруться з ідентифікаторів моделі; схема гарантує, що це малі латинські літери, цифри, дефіс і підкреслення. Ім'я організації для топології — фіксоване `lab`, бо поле `organization` у моделі довільний текст.

Каталог виходу належить `orgc`:

| Варіант | Застарілі файли | Ризик для чужих файлів |
|---|---|---|
| A. Лише дописувати | лишаються, E5 бачить шум | немає |
| **B. Перезаписувати повністю, якщо каталог позначено маркером** | зникають | немає: без маркера `orgc` відмовляє |
| C. Перезаписувати будь-який каталог | зникають | є |

Рішення — B. Новий прогін пише дерево в тимчасовий каталог поруч і замінює ним старий; файли, яких новий прогін не генерує, зникають. Непорожній каталог без маркера `orgc` не чіпає й завершується з кодом 2. Маркер містить лише фіксований текст, без часу.

## 3. Фізичні порти

Модель v2 описує мережі, ролі й адреси, але не інтерфейси й не лінки між пристроями. Бекенду ж треба знати, який порт дивиться назовні, а які несуть VLAN сайту.

Рішення — конвенція платформи, модель не змінюється:

| Роль | RouterOS (родина RB750/hEX) | Arista EOS |
|---|---|---|
| L3-шлюз сайту (`edge_router`, `firewall`) | `ether1` — маршрутизований uplink: власна адреса, вихід назовні, NAT; `ether2`–`ether5` — один bridge з VLAN-фільтрацією, trunk з усіма VLAN сайту; адреси шлюзів мереж — на VLAN-інтерфейсах поверх bridge | `Ethernet1` — маршрутизований uplink; решта — trunk; шлюзи мереж — SVI `Vlan<N>` |
| комутатор (`access_switch`, `distribution_switch`, `core_switch`) | `ether1` — trunk до шлюзу сайту; адреса керування — на VLAN-інтерфейсі mgmt-мережі | `Ethernet1` — trunk до шлюзу сайту; керування — SVI mgmt-мережі |

Отже, на шлюзі частина портів маршрутизується (uplink), частина комутується (bridge), а маршрутизація між мережами сайту йде на VLAN-інтерфейсах. Топологія сайту за цією конвенцією — зірка: кожен комутатор з'єднаний безпосередньо зі шлюзом.

Відкрите питання. Ролі `access_switch`, `distribution_switch` і `core_switch` у моделі є, але ієрархію Access → Distribution → Core конвенція не виражає: для неї потрібні лінки між пристроями (чи порти пристроїв) у моделі. Призначення access-портів окремим VLAN модель v2 теж не описує. Розширення моделі — окреме рішення щодо її семантики; до нього бекенди генерують зірку, а обмеження записано в `docs/data-model.md`.

## 4. Інвентар Ansible і еталон

Групи — за платформою, назви збережено там, де від них залежать плейбуки:

| Група | Хто потрапляє | Змінні групи (від платформи) |
|---|---|---|
| `linux_servers` | сервери моделі | `ansible_user: ansible-svc` |
| `mikrotik_routers` | пристрої `mikrotik` | `ansible_connection: local`, `routeros_api_username`, `routeros_api_password` через `lookup('env', 'ROUTEROS_PASSWORD')` |
| `arista_switches` | пристрої `arista_eos` | `network_cli`, `arista.eos.eos`, пароль через змінну vault |

`ansible_host` — `mgmt_ip` пристрою чи `ip` сервера. Порожня група `cisco_switches` зникає (Cisco в роботі не використовується), `env_name` з `group_vars/all` теж: його ніхто не читає.

Еталон. Наявний `ansible/inventories/staging/` описує реальний стенд у плоскій мережі `192.168.1.0/24` (RB750 на .220, ctrl-01 на .50), а `organization.s-profile.yml` — цільову сегментовану мережу `192.168.10.0/24` тощо.

| Варіант | Що буде з `smoke_routeros.yml` | Що описує еталон |
|---|---|---|
| A. Еталон — вихід із `s-profile` | перестане діставати RB750, доки не побудовано цільову мережу | мережу, якої ще немає |
| **B. Нова модель поточного стенда, еталон — її вихід** | працює без змін | стенд, який є |

Рішення — B. Модель `examples/organization.lab.yml` описує поточний стенд: одна mgmt-мережа `192.168.1.0/24` без `gateway` (домашній роутер не є пристроєм моделі), rb750 на .220, сервери ctrl-01 і mon-01 на .50 і .51, вузол керування в тій самій мережі. `ansible/inventories/staging/` стає виходом `orgc render` з цієї моделі; golden-тест бекенда `ansible` звіряє вихід з ним побайтово. Та сама модель — відправна точка наскрізного експерименту на живому обладнанні.

## 5. Семантика політик у бекендах

Правила моделі лише відкривають потоки, діють stateful і нетранзитивно (`docs/data-model.md`). На L3-шлюзі сайту це стає:

| Ланцюжок | Порядок |
|---|---|
| forward | `established,related` → accept; `invalid` → drop; правила моделі в канонічному порядку; наприкінці drop |
| input (до самого шлюзу) | `established,related` → accept; правила моделі, чиє призначення містить адресу шлюзу в цій мережі; DHCP (udp/67) з мереж із пулом; наприкінці drop |
| srcnat | masquerade через uplink для мереж, яким правило відкриває `internet` |

- Input потрібен, бо адреса шлюзу (і його `mgmt_ip`) лежить у мережі, яку правило відкриває: правило `servers → mgmt` на порт 8728 відкриває й API самого маршрутизатора. Інакше E006 підтвердив би доступ, якого конфігурація не дає.
- `any` розгортається в усі мережі моделі, `internet` — в «через uplink, не в мережі моделі».
- Канонічний порядок правил: за `from`, `to`, протоколом, портами. Порядок правил моделі значення не має (лише allow), а сортування дає E5 локальність: нове правило змінює кілька сусідніх рядків.
- Ізоляція клієнтів: на RouterOS — bridge filter, що забороняє L2-трафік між портами всередині VLAN мережі з `isolated: true`; на EOS — private VLAN з isolated VLAN. Обидва ізолюють хостів, підключених до портів самого пристрою.
- Можливості немає (W002 уже попередив): бекенд генерує те, що платформа вміє, а на місці решти пише коментар з назвою відсутньої можливості. Нічого не пропускається мовчки.

## 6. Топологія containerlab

| Тип пристрою | Вид вузла | Образ |
|---|---|---|
| `arista_eos` | `arista_ceos` | `ceos:<os_version>` |
| `mikrotik` | `mikrotik_ros` (vrnetlab) | `vrnetlab/mikrotik_routeros:<os_version>` (CHR) |

- Сервери в топологію не входять: це VM на гіпервізорі.
- Лінки — з конвенції портів (рішення 3): uplink-порт кожного комутатора ↔ наступний trunk-порт шлюзу свого сайту; uplink-порти шлюзів усіх сайтів ↔ спільний вузол-міст `wan`. Міст відтворює припущення моделі про повнозв'язні міжсайтові з'єднання.
- Змішування емульованих вузлів із реальним обладнанням (RB750 на стенді) передбачене ще ADR-003; спосіб підключення фізичного пристрою до топології — разом із відкритим питанням рішення 3.

## 7. Детермінованість

- Перший рядок кожного файлу — коментар `Згенеровано orgc з <ім'я файлу моделі>. Не редагувати вручну.` у синтаксисі формату. Без часу й без версії `orgc`: версія змінювала б кожен файл при кожному релізі. Ім'я файлу моделі — без шляху, бо шлях залежить від того, звідки запущено `orgc`.
- Порядок усюди, де модель його не задає, — сортування; де задає — порядок файлу.
- LF, UTF-8, порожній рядок наприкінці файлу.
- Golden-тести: `orgc/testdata/golden/<модель>/<дерево виходу>`, побайтове порівняння всього дерева, оновлення еталонів — `go test ./... -update`.

## Наслідки

- (+) Генерація з моделі з помилками неможлива за побудовою.
- (+) Diff двох прогонів містить лише справжні зміни: застарілі файли зникають, порядок канонічний, заголовки не змінюються.
- (+) Нова платформа додається реалізацією `Platform` (з `Render`) і, за потреби, `AnsibleTarget` та `LabNode`; генератори не змінюються.
- (+) Інвентар staging перестає бути ручним файлом, що розходиться з моделлю: його породжує `orgc`, і golden-тест це стереже.
- (−) Конвенція портів дає лише зірку від шлюзу. Ієрархія Access/Distribution/Core і призначення access-портів потребують розширення моделі.
- (−) Ізоляція клієнтів діє лише на портах пристрою, що її реалізує.
- (−) Каталог виходу без маркера `orgc` перезаписувати відмовляється; користувач, який вказав наявний каталог з іншими файлами, отримає код 2 і має вказати інший.

## Поправка 2026-10-12: зʼєднання в моделі

Модель отримала зʼєднання між пристроями (`sites[].links`), порти серверів, access-порти й порти каналів (`docs/data-model.md`, розділ про зʼєднання). Рішення 3 і 6 уточнюються; решта лишається без змін.

Рішення 3, порти:

| Сайт | Звідки бекенд бере порти |
|---|---|
| із `links` | лише з моделі: кінці зʼєднань — trunk з VLAN зі списку `vlans` (без поля — усі мережі сайту), `access_ports` і `servers[].port` — access-порти у VLAN своєї мережі, `uplinks[].port` — маршрутизований uplink шлюзу |
| без `links` | конвенція з рішення 3: зірка від шлюзу, кожен комутатор підключений першим портом, trunk несе всі мережі сайту |

- Порт каналу без `port` береться за конвенцією платформи в обох випадках (`ether1`, `Ethernet1`).
- Порти, не згадані в моделі, бекенд не налаштовує й не вимикає: вони лишаються такими, як були на пристрої. Вимикати їх без винятку не можна, бо на RB750 порт `ether5` використовується для аварійного доступу WinBox за MAC-адресою. З тієї самої причини конвенція для RouterOS бере в trunk `ether2`–`ether4`, а не `ether2`–`ether5`.
- Чи припустиме імʼя порту для платформи, перевіряє `orgc verify`: платформа оголошує шаблон імен (RouterOS: `ether<N>`, `sfp<N>`, `sfp-sfpplus<N>`; EOS: `Ethernet<N>` чи `Ethernet<N>/<M>`), невідповідність — W002 рівня помилки. Для цього інтерфейс платформи отримує метод `CheckPort`.

Рішення 6, containerlab: лінки топології беруться з `links` сайту, якщо вони є; інакше — з конвенції портів, як і раніше. Міст `wan` між uplink-портами шлюзів лишається.
