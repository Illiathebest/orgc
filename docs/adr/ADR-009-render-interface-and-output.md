# ADR-009: Інтерфейс рендеру і контракт виходу `orgc render`

- **Статус:** Accepted. Рішення: **рендер пристрою виконує метод платформи, рендер рівня моделі виконують окремі генератори; `render` лише після чистого `verify`; каталог виходу належить `orgc` і перезаписується повністю; порти беруться з моделі, для сайту без зʼєднань діє конвенція платформи (поправка 2026-10-12); еталоном інвентаря є вихід з моделі поточного стенда**
- **Дата:** 2026-10-12
- Контекст: `orgc verify` перевіряє модель повністю (ADR-008), а `orgc render` поки що заглушка. Генерація має дати конфігурації RouterOS і Arista EOS, інвентар Ansible, цілі Prometheus і топологію containerlab. Від рішень нижче залежать усі бекенди, golden-тести й експеримент E5 (локальність diff). Якщо зміна одного правила моделі тягне зміни в непов'язаних файлах чи лишає застарілі файли, E5 вимірюватиме шум.

ADR відповідає на сім питань:

1. як бекенд отримує модель і що повертає;
2. яке дерево виходу і що буває з наявним каталогом;
3. звідки бекенд знає фізичні порти, яких модель не описує;
4. що генерується для Ansible і що вважати еталоном;
5. як правила політики стають конфігурацією на кожній платформі;
6. з чого будується топологія containerlab;
7. що гарантує побайтову детермінованість.

## Вимоги

1. Ядро не знає вендорів (ADR-008). Пакети `ir`, `lower`, `verify` і інтерфейс `backend` не імпортують платформних пакетів.
2. Детермінованість. Той самий вхід дає побайтово той самий вихід, зокрема між версіями `orgc`, якщо генерація не змінювалась.
3. Конфігурація генерується лише з перевіреної моделі. Те, що `verify` вважає помилкою, на обладнання не потрапляє.
4. Наявні плейбуки (`smoke_routeros.yml`, `linux.yml`) працюють на згенерованому інвентарі без змін.
5. Секрети не з'являються у виході. Там є лише посилання на `ansible-vault` чи змінні середовища.

## 1. Інтерфейс рендеру

```go
// package backend
type File struct {
    Path string // відносний, через "/", напр. "configs/hq/rb750.rsc"
    Data []byte
}

type Platform interface {
    // ... методи ADR-008: Type, CheckVersion, ManagementPorts, Capabilities
    Render(m *ir.Model, d *ir.Device) []File
}

type Generator interface {
    Name() string
    Generate(m *ir.Model, p Platforms) []File
}
```

- Конфігурацію пристрою рендерить його платформа. Усе, що стосується синтаксису RouterOS чи EOS, живе в її пакеті.
- Ansible, Prometheus і containerlab описують модель цілком. Тому це окремі генератори з реєстром у `cmd/orgc` у фіксованому порядку.
- Іноді генераторові потрібне знання про платформу: група інвентаря й змінні підключення, вид вузла containerlab. Тоді він питає платформу через додатковий інтерфейс, який вона реалізує, наприклад `AnsibleTarget` чи `LabNode`. Генератор вендорів не знає.
- На вході лише IR і реєстр платформ. Повернення помилки не передбачено, оскільки модель уже перевірена. Неможливість згенерувати пристрій – це W002 рівня помилки, про яку `verify` повідомив раніше.

`orgc render <модель> -o <каталог>` спершу виконує той самий конвеєр, що й `verify`:

| Результат `verify` | `render` |
|---|---|
| помилки (зокрема W002 рівня помилки) | діагностики, код 1, жодного файлу |
| лише попередження | діагностики, генерація, код 0 |
| нічого | генерація, код 0 |

## 2. Дерево виходу

```
<каталог>/
  .orgc-output                         маркер: каталог створено orgc
  configs/<site>/<device>.rsc          RouterOS
  configs/<site>/<device>.cfg          Arista EOS
  ansible/hosts.yml
  ansible/group_vars/<group>/main.yml
  prometheus/targets/<job>.json        file_sd
  containerlab/<organization>.clab.yml
```

Імена каталогів і файлів беруться з ідентифікаторів моделі. Схема гарантує, що це малі латинські літери, цифри, дефіс і підкреслення. Ім'я організації для топології фіксоване, `lab`, оскільки поле `organization` у моделі містить довільний текст.

Каталог виходу належить `orgc`. Розглянуто три варіанти:

| Варіант | Застарілі файли | Ризик для чужих файлів |
|---|---|---|
| A. Лише дописувати | лишаються, E5 бачить шум | немає |
| **B. Перезаписувати повністю, якщо каталог позначено маркером** | зникають | немає: без маркера `orgc` відмовляє |
| C. Перезаписувати будь-який каталог | зникають | є |

Обрано варіант B. Новий прогін пише дерево в тимчасовий каталог поруч і замінює ним старий. Файли, яких новий прогін не генерує, зникають. Непорожнього каталогу без маркера `orgc` не чіпає і завершується з кодом 2. Маркер містить лише фіксований текст, без часу.

## 3. Фізичні порти

Модель v2 описує мережі, ролі й адреси, але не описує інтерфейсів і лінків між пристроями. Однак бекенду треба знати, який порт дивиться назовні, а які несуть VLAN сайту.

Обрано конвенцію платформи, модель при цьому не змінюється:

| Роль | RouterOS (родина RB750/hEX) | Arista EOS |
|---|---|---|
| L3-шлюз сайту (`edge_router`, `firewall`) | `ether1` — маршрутизований uplink: власна адреса, вихід назовні, NAT; `ether2`–`ether5` — один bridge з VLAN-фільтрацією, trunk з усіма VLAN сайту; адреси шлюзів мереж — на VLAN-інтерфейсах поверх bridge | `Ethernet1` — маршрутизований uplink; решта — trunk; шлюзи мереж — SVI `Vlan<N>` |
| комутатор (`access_switch`, `distribution_switch`, `core_switch`) | `ether1` — trunk до шлюзу сайту; адреса керування — на VLAN-інтерфейсі mgmt-мережі | `Ethernet1` — trunk до шлюзу сайту; керування — SVI mgmt-мережі |

Отже, на шлюзі частина портів маршрутизується (uplink), частина комутується (bridge), а маршрутизація між мережами сайту йде на VLAN-інтерфейсах. За цією конвенцією топологія сайту має форму зірки. Кожен комутатор з'єднаний безпосередньо зі шлюзом.

Відкрите питання. Ролі `access_switch`, `distribution_switch` і `core_switch` у моделі є, але ієрархію Access → Distribution → Core конвенція не виражає. Для неї в моделі потрібні лінки між пристроями чи порти пристроїв. Призначення access-портів окремим VLAN модель v2 теж не описує. Розширення моделі – це окреме рішення щодо її семантики. До нього бекенди генерують зірку, а обмеження записано в `docs/data-model.md`.

## 4. Інвентар Ansible і еталон

Групи визначаються платформою. Назви збережено там, де від них залежать плейбуки:

| Група | Хто потрапляє | Змінні групи (від платформи) |
|---|---|---|
| `linux_servers` | сервери моделі | `ansible_user: ansible-svc` |
| `mikrotik_routers` | пристрої `mikrotik` | `ansible_connection: local`, `routeros_api_username`, `routeros_api_password` через `lookup('env', 'ROUTEROS_PASSWORD')` |
| `arista_switches` | пристрої `arista_eos` | `network_cli`, `arista.eos.eos`, пароль через змінну vault |

`ansible_host` – це `mgmt_ip` пристрою чи `ip` сервера. Порожня група `cisco_switches` зникає, бо Cisco в роботі не використовується. Зникає й `env_name` з `group_vars/all`, бо його ніхто не читає.

Еталон. Наявний `ansible/inventories/staging/` описує реальний стенд у плоскій мережі `192.168.1.0/24` (RB750 на .220, ctrl-01 на .50). Натомість `organization.s-profile.yml` описує цільову сегментовану мережу `192.168.10.0/24` тощо.

| Варіант | Що буде з `smoke_routeros.yml` | Що описує еталон |
|---|---|---|
| A. Еталон — вихід із `s-profile` | перестане діставати RB750, доки не побудовано цільову мережу | мережу, якої ще немає |
| **B. Нова модель поточного стенда, еталон — її вихід** | працює без змін | стенд, який є |

Обрано варіант B. Модель `examples/organization.lab.yml` описує поточний стенд. У ній одна mgmt-мережа `192.168.1.0/24` без `gateway`, бо домашній роутер не є пристроєм моделі. rb750 стоїть на .220, сервери ctrl-01 і mon-01 мають адреси .50 і .51, а вузол керування стоїть у тій самій мережі. `ansible/inventories/staging/` стає виходом `orgc render` з цієї моделі. Golden-тест бекенда `ansible` побайтово звіряє вихід з ним. Ця ж модель є відправною точкою наскрізного експерименту на живому обладнанні.

## 5. Семантика політик у бекендах

Правила моделі лише відкривають потоки, діють stateful і нетранзитивно (`docs/data-model.md`). На L3-шлюзі сайту вони перетворюються так:

| Ланцюжок | Порядок |
|---|---|
| forward | `established,related` → accept; `invalid` → drop; правила моделі в канонічному порядку; наприкінці drop |
| input (до самого шлюзу) | `established,related` → accept; правила моделі, чиє призначення містить адресу шлюзу в цій мережі; DHCP (udp/67) з мереж із пулом; наприкінці drop |
| srcnat | masquerade через uplink для мереж, яким правило відкриває `internet` |

- Ланцюжок input потрібен, оскільки адреса шлюзу і його `mgmt_ip` лежать у мережі, яку відкриває правило. Наприклад, правило `servers → mgmt` на порт 8728 відкриває й API самого маршрутизатора. Без input E006 підтвердив би доступ, якого конфігурація не дає.
- `any` розгортається в усі мережі моделі. `internet` означає «через uplink, не в мережі моделі».
- Правила йдуть у канонічному порядку: за `from`, `to`, протоколом, портами. Порядок правил у моделі значення не має, бо правила лише дозволяють. Сортування дає E5 локальність: нове правило змінює кілька сусідніх рядків.
- Ізоляція клієнтів. На RouterOS це bridge filter, що забороняє L2-трафік між портами всередині VLAN мережі з `isolated: true`. На EOS це private VLAN з isolated VLAN. Обидва варіанти ізолюють хостів, підключених до портів самого пристрою.
- Якщо можливості немає, W002 уже про це попередив. Бекенд генерує те, що платформа вміє, а на місці решти пише коментар з назвою відсутньої можливості. Мовчки нічого не пропускається.

## 6. Топологія containerlab

| Тип пристрою | Вид вузла | Образ |
|---|---|---|
| `arista_eos` | `arista_ceos` | `ceos:<os_version>` |
| `mikrotik` | `mikrotik_ros` (vrnetlab) | `vrnetlab/mikrotik_routeros:<os_version>` (CHR) |

- Сервери в топологію не входять, бо це VM на гіпервізорі.
- Лінки беруться з конвенції портів (рішення 3). Uplink-порт кожного комутатора з'єднано з наступним trunk-портом шлюзу свого сайту. Uplink-порти шлюзів усіх сайтів з'єднано зі спільним вузлом-мостом `wan`. Міст відтворює припущення моделі про повнозв'язні міжсайтові з'єднання.
- Змішування емульованих вузлів із реальним обладнанням (RB750 на стенді) передбачене ще ADR-003. Спосіб підключення фізичного пристрою до топології вирішується разом із відкритим питанням рішення 3.

## 7. Детермінованість

- Перший рядок кожного файлу – коментар `Згенеровано orgc з <ім'я файлу моделі>. Не редагувати вручну.` у синтаксисі формату. У ньому немає часу й версії `orgc`, бо версія змінювала б кожен файл при кожному релізі. Ім'я файлу моделі пишеться без шляху, оскільки шлях залежить від того, звідки запущено `orgc`.
- Там, де модель не задає порядку, вихід сортується. Там, де задає, зберігається порядок файлу.
- LF, UTF-8, порожній рядок наприкінці файлу.
- Golden-тести лежать у `orgc/testdata/golden/<модель>/<дерево виходу>` і порівнюють усе дерево побайтово. Еталони оновлює `go test ./... -update`.

## Наслідки

- (+) Генерація з моделі з помилками неможлива за побудовою.
- (+) Diff двох прогонів містить лише справжні зміни. Застарілі файли зникають, порядок канонічний, заголовки не змінюються.
- (+) Нова платформа додається реалізацією `Platform` (з `Render`) і, за потреби, `AnsibleTarget` та `LabNode`. Генератори при цьому не змінюються.
- (+) Інвентар staging більше не є ручним файлом, що розходиться з моделлю. Його породжує `orgc`, і golden-тест це перевіряє.
- (−) Конвенція портів дає лише зірку від шлюзу. Ієрархія Access/Distribution/Core і призначення access-портів потребують розширення моделі.
- (−) Ізоляція клієнтів діє лише на портах пристрою, який її реалізує.
- (−) Каталог виходу без маркера `orgc` перезаписувати відмовляється. Користувач, який вказав наявний каталог з іншими файлами, отримає код 2 і має вказати інший.

## Поправка 2026-10-12: зʼєднання в моделі

Модель отримала зʼєднання між пристроями (`sites[].links`), порти серверів, access-порти й порти каналів (`docs/data-model.md`, розділ про зʼєднання). Рішення 3 і 6 уточнюються, решта лишається без змін.

Рішення 3, порти:

| Сайт | Звідки бекенд бере порти |
|---|---|
| із `links` | лише з моделі: кінці зʼєднань — trunk з VLAN зі списку `vlans` (без поля — усі мережі сайту), `access_ports` і `servers[].port` — access-порти у VLAN своєї мережі, `uplinks[].port` — маршрутизований uplink шлюзу |
| без `links` | конвенція з рішення 3: зірка від шлюзу, кожен комутатор підключений першим портом, trunk несе всі мережі сайту |

- Порт каналу без `port` береться за конвенцією платформи в обох випадках (`ether1`, `Ethernet1`).
- Порти, не згадані в моделі, бекенд не налаштовує й не вимикає. Вони лишаються такими, як були на пристрої. Вимикати їх без винятку не можна, бо на RB750 порт `ether5` використовується для аварійного доступу WinBox за MAC-адресою. З тієї самої причини конвенція для RouterOS бере в trunk `ether2`–`ether4` замість `ether2`–`ether5`.
- Чи припустиме імʼя порту для платформи, перевіряє `orgc verify`. Платформа оголошує шаблон імен. Для RouterOS це `ether<N>`, `sfp<N>`, `sfp-sfpplus<N>`, для EOS це `Ethernet<N>` чи `Ethernet<N>/<M>`. Невідповідність дає W002 рівня помилки. Для цього інтерфейс платформи отримує метод `CheckPort`.

Рішення 6, containerlab. Лінки топології беруться з `links` сайту, якщо вони є, інакше з конвенції портів, як і раніше. Міст `wan` між uplink-портами шлюзів лишається.

Уточнення за реалізацією бекендів, рішення 5 і 7:

- Ізоляцію клієнтів на RouterOS реалізовано спільним `horizon` на access-портах ізольованої мережі замість bridge filter. Порти з однаковим `horizon` не передають кадри один одному, а до шлюзу хости доходять.
- Ізоляцію клієнтів на EOS реалізовано вхідним ACL на access-портах ізольованої мережі. Він дозволяє трафік до шлюзу, DHCP і все поза мережею та забороняє трафік до інших хостів мережі. Private VLAN відхилено. Йому потрібен вторинний VLAN, якого модель не задає, і перетворення вторинного VLAN на первинний на кожному trunk аж до шлюзу.
- Скрипт RouterOS містить лише ASCII, а його заголовок написано англійською (`Generated by orgc from …`). RouterOS 6 ненадійно обробляє не-ASCII у скриптах. Інші формати мають український заголовок з рішення 7.
- Скрипт RouterOS розрахований на пристрій, скинутий без заводської конфігурації. У заводській конфігурації вже є міст, списки інтерфейсів і DHCP-клієнт, і їх створення у скрипті падало б.
- containerlab (рішення 6). Міст `wan` прибрано, uplink-порти шлюзів у топологію не входять. Образ vrnetlab RouterOS займає `ether1` під мережу керування containerlab, а дані йдуть з `ether2` = `eth1`. Тому uplink маршрутизатора до моста не підключити. Водночас мережа керування containerlab і так зʼєднує всі вузли між собою й назовні. Так відтворюється припущення моделі про повнозвʼязні сайти. Відповідність портів інтерфейсам вузла дає платформа через інтерфейс `LabNode`: RouterOS `etherN` → `eth(N-1)`, EOS `EthernetN` → `ethN`, `EthernetN/M` → `ethN_M`. Зʼєднання, яке емуляція не відтворює (кінець на `ether1` RouterOS), позначається коментарем у топології.

## Поправка 2026-10-13: емуляційний стенд

Рішення 6 уточнює [ADR-010](ADR-010-emulation-stand.md). Топологія задає мережу керування `10.99.1.0/24` з фіксованою адресою кожного вузла. Сервер, у якого в моделі є `port` на емульованому пристрої, стає вузлом Linux з адресою й маршрутом за замовчуванням із моделі. Сервери без `port` у топологію, як і раніше, не входять.

## Поправка 2026-10-14: резервні зʼєднання і RSTP

Модель отримала резервні зʼєднання (`links[].standby`, `docs/data-model.md`). Перевірки працюють на дереві активних зʼєднань. Тому бекенди мають налаштувати STP так, щоб після збіжності активна топологія збігалася з цим деревом. Без явних налаштувань STP обрав би корінь і заблокований порт за MAC-адресами, яких у моделі немає.

| | RouterOS 6.x | EOS |
|---|---|---|
| протокол | `protocol-mode=rstp` на мосту | `spanning-tree mode rstp` замість типового MSTP |
| корінь — L3-шлюз сайту | `priority=0x1000` | `spanning-tree priority 4096` |
| інші пристрої | `priority=0x8000` | типовий пріоритет |
| порт резервного зʼєднання, обидва кінці | `path-cost=200000000` | `spanning-tree cost 200000000` |

- Будь-який шлях без резервних зʼєднань є шляхом дерева, і він дешевший за 200 000 000. Тому жоден міст не обере кореневим портом порт резервного зʼєднання. На сегменті резервного зʼєднання один із портів стає `alternate`.
- Для всіх VLAN використовується один екземпляр дерева, бо модель не задає різних топологій для різних VLAN.
- RSTP вмикається на всіх пристроях усіх сайтів, навіть там, де немає резервних зʼєднань. Інакше додавання першого резервного зʼєднання змінювало б конфігурацію кожного пристрою сайту, і діф був би нелокальним.
- Налаштування перевірено на емуляції `m-profile`. Коренем стає L3-шлюз, порти резервних зʼєднань на access-комутаторах переходять у стан `alternate`/`discarding`, а всі пристрої приймають конфігурацію повністю.
- Containerlab позначає резервні лінки коментарем `# резервне`.

## Поправка 2026-10-14b: список мереж моделі на RouterOS

Шлюз RouterOS отримував список `orgc-networks` з усіма мережами моделі, по окремому запису на кожну. Список потрібен лише правилам з `any` (`src-address-list` / `dst-address-list`), а інтернет виражено через `out-interface-list=WAN`. Через це конфігурація кожного шлюзу росла разом з усією моделлю. На моделі з 1000 пристроїв це 400 рядків на кожному з 50 шлюзів, разом 20 000 з 23 446 рядків `.rsc`. Крім того, нова мережа будь-якого сайту змінювала всі шлюзи RouterOS.

Після поправки:

- список виводиться лише на шлюзі, серед правил якого є `any`;
- префікси агрегуються. Вкладений префікс поглинається, а дві половини одного префікса стають цим префіксом, доки є що обʼєднати. Список покриває ті самі адреси, що й мережі моделі. Коментар запису містить імʼя мережі, якщо запис покриває одну мережу, інакше кількість мереж.

Семантика правил не змінюється.
