# Модель даних `organization.yml`

> Серце концепції **Organization-as-Data** (CONCEPT §2). Адміністратор описує свою організацію в одному декларативному файлі — а платформа компілює його у конфігурації мережі, серверів і моніторингу. Цей документ пояснює **кожне поле простою мовою**.

Формальний контракт — `schema/organization.schema.json` (JSON Schema 2020-12). Вибір саме JSON Schema обґрунтовано в [ADR-005](../../docs/adr/ADR-005-data-model-validation.md). На кожен Merge Request CI-стадія `validate` перевіряє файл проти схеми: помилка у структурі — червоний пайплайн.

## Як підключити підказки в редакторі

Додайте першим рядком файлу коментар — і VS Code (з розширенням YAML) підсвічуватиме помилки прямо під час набору:

```yaml
# yaml-language-server: $schema=../schema/organization.schema.json
```

## Структура верхнього рівня

| Поле | Обовʼязкове | Тип | Призначення |
|---|---|---|---|
| `organization` | так | рядок | Людська назва компанії. |
| `profile` | так | `S` \| `M` \| `L` | Профіль масштабування — визначає топологію control plane. |
| `sites` | так | список | Майданчики (локації) організації. |
| `policies` | ні | обʼєкт | Правила доступу між мережами. |
| `modules` | ні | обʼєкт | Які функціональні модулі ввімкнено. |

### `organization`

Назва організації-власника інфраструктури, напр. `"Навчальна лабораторія"`. Будь-який непорожній рядок.

### `profile`

Один із трьох профілів масштабування (CONCEPT §4):

- **`S`** — малий офіс (до ~50 користувачів), увесь control plane на одному вузлі.
- **`M`** — кілька сайтів (50–500), виділений control node у HQ, звʼязок між сайтами через WireGuard.
- **`L`** — корпорація (500+), HA-GitLab, runner на кожному сайті.

Перехід S→M→L — це зміна цього поля + міграційний плейбук, без переписування конфігів.

## `sites[]` — майданчики

Список локацій. Мінімум один. Кожен сайт:

| Поле | Обовʼязкове | Тип | Призначення |
|---|---|---|---|
| `name` | так | ідентифікатор | Коротке імʼя сайту, напр. `hq`, `branch`. |
| `networks` | так | список | VLAN-сегменти сайту (мінімум один). |
| `devices` | ні | список | Мережеві пристрої сайту. |
| `servers` | ні | список | Сервери сайту. |

> **Ідентифікатор** усюди в моделі — малі латинські літери, цифри, дефіс і підкреслення, починається з літери (напр. `hq`, `rb750`, `sw-branch-01`). Це гарантує, що зі значень безпечно генерувати імена в Ansible/конфігах.

### `sites[].networks[]` — мережі (VLAN-сегменти)

| Поле | Обовʼязкове | Тип | Призначення |
|---|---|---|---|
| `vlan` | так | ціле 1–4094 | Номер VLAN. |
| `name` | так | ідентифікатор | Роль сегмента: `mgmt`, `users`, `servers`, `guest`. |
| `cidr` | так | CIDR | Підмережа, напр. `192.168.10.0/24`. |
| `isolated` | ні | булеве | `true` — трафік сегмента ізольовано (типово для `guest`). |

**CIDR** — це адреса мережі з префіксом довжини: `192.168.10.0/24` означає «мережа 192.168.10.x з 256 адрес». Префікс — 0–32.

### `sites[].devices[]` — мережеві пристрої

| Поле | Обовʼязкове | Тип | Призначення |
|---|---|---|---|
| `name` | так | ідентифікатор | Імʼя пристрою, напр. `rb750`. |
| `type` | так | `mikrotik` \| `cisco_ios` | Платформа автоматизації (визначає, яка Ansible-колекція керує пристроєм). |
| `role` | так | див. нижче | Призначення у топології. |
| `mgmt_ip` | так | IPv4 | Адреса керування (доступна лише з mgmt VLAN). |

Дозволені ролі `role`: `edge_router`, `access_switch`, `core_switch`, `distribution_switch`, `firewall`.

### `sites[].servers[]` — сервери

| Поле | Обовʼязкове | Тип | Призначення |
|---|---|---|---|
| `name` | так | ідентифікатор | Імʼя сервера, напр. `ctrl-01`. |
| `role` | так | список ролей | Одна або кілька ролей навантаження. |
| `ip` | так | IPv4 | Адреса сервера. |

`role` — це **список** (навіть для однієї ролі): `[docker_host]` або `[docker_host, monitoring]`. Дозволені значення: `docker_host`, `monitoring`, `siem`, `identity`, `app`.

## `policies` — політики безпеки

За замовчуванням між VLAN діє **default-deny**: усе заборонено, поки правило явно не дозволить (CONCEPT §6). Зараз модель описує правила міжмережевого доступу:

### `policies.inter_vlan[]`

| Поле | Обовʼязкове | Тип | Призначення |
|---|---|---|---|
| `from` | так | рядок | Мережа-джерело (назва сегмента або `any`). |
| `to` | так | рядок | Мережа-призначення (назва або `any`). |
| `ports` | ні | список цілих | TCP/UDP-порти (1–65535). |
| `action` | так | `allow` \| `deny` | Дозволити чи заборонити. |
| `except` | ні | рядок | Виняток, напр. `internet` — дозволити лише вихід в інтернет. |

Приклади:

```yaml
- { from: users, to: servers, ports: [443, 22], action: allow }
- { from: guest, to: any, action: deny, except: internet }
```

## `modules` — функціональні модулі

Прапорці, що вмикають незалежні модулі платформи (CONCEPT §3). Невідомі ключі заборонені (схема їх відхилить).

| Поле | Тип | Що вмикає |
|---|---|---|
| `network_fabric` | булеве | VLAN, ACL/firewall, VPN; Cisco/MikroTik з коду. |
| `security_observability` | булеве | Prometheus/Grafana/Loki, логи, Wazuh SIEM, drift detection. |
| `server_services` | булеве | Hardening ОС, Docker-платформа, типові сервіси. |
| `identity_access` | булеве | FreeIPA + Keycloak, адаптер Samba AD. |

## Повний приклад

Робочі приклади під наш стенд — у каталозі `examples/`:

- `organization.s-profile.yml` — профіль S (один вузол HQ: RB750 + ctrl-01 + mon-01);
- `organization.m-profile.yml` — профіль M (HQ + філія, WireGuard між сайтами);
- `organization.broken.yml` — навмисно зламаний приклад для негативного тесту CI.

## Що поки поза охопленням схеми

JSON Schema гарантує **структуру** (типи, переліки, формати), але не **семантичні звʼязки**: неперетин діапазонів CIDR, унікальність VLAN-ID у межах сайту, відповідність `policies` принципу default-deny. Ці перевірки заплановано окремим шаром політик у M3+ (кандидати — OPA/`conftest` або власний валідатор), див. розділ «Наслідки» в [ADR-005](../../docs/adr/ADR-005-data-model-validation.md).
